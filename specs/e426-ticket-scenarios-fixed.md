## Problem Statement

The v5 chain treats a ticket file's scenarios as the contract (qa-engineer tests each one, code-reviewer judges against them, the server checks one acceptance line per scenario when the spec cites the ticket file), but the pm SOP still tells pm to author Given/When/Then acceptance criteria itself, with `proof:` only "where feasible", and says nothing about ticket files. No SOP says what happens when a case the scenarios miss turns up during the work: the ticket format allows appending a scenario under `## Added during build` but does not say who may append or when a case must stop the ticket instead, its own example shows "the implementer" appending (the role that must not), sr-engineer's return route covers only a test that contradicts a scenario, and code-reviewer's clean context does not read `## Added during build` at all, so an appended scenario is never judged. The ticket's audit amendment (human ruling 11, 2026-11-19) fixes the rule: the spec cites the ticket's scenarios and copies none; a case that extends decided behaviour is appended (by pm at the cut or qa-engineer while writing tests, marked with who, date, reason and verification); a case that decides new behaviour stops the ticket; an interface detail is qa-engineer's decision. Two open items need a human ruling: whether small ticket-file tickets may skip pm (re-derived below against today's server entry rules), and whether the ticket format's example line is fixed.

## User Stories

- As a pm on a ticket-file ticket, I want to cite the ticket's scenarios instead of rewriting them, so that the spec cannot drift from the contract the human agreed and the server's per-scenario check reads the same ids.
- As a qa-engineer, I want a stated rule for a case the scenarios miss, so that I append what extends decided behaviour (with marks), stop on what decides new behaviour, and decide interface details myself.
- As an sr-engineer, I want a return route for a case no scenario covers, so that I never build untested behaviour or write a test myself.
- As a code-reviewer, I want to read `## Added during build` and reject a missing or unmarked case, so that appended scenarios are judged like the original ones.
- As a person or agent without agc reading the ticket format, I want the appending rule and an example that agrees with it, so that I do not learn the opposite rule from the example.

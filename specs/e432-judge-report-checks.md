## Problem Statement

After E431 a code-reviewer PASS on a marked (test-first) feature passes the transition and judge-identity checks, but the PASS-time evidence checks still assume qa-engineer is the judge: the completion-evidence check (`QA_COMPLETION_EVIDENCE_MISSING`) arms only on qa-engineer writes, so a code-reviewer write that grows `completed_tasks` on a marked feature is not evidence-checked at all; `MISSING_EVIDENCE`, `EXPECTED_RED_DIFF_MISSING` and `AC_EXECUTION_LOG_MISSING` look only at qa-engineer's report location; drift detection, the archive-aware evidence lookup, `tools/lane-status.ts` and `scripts/release.mjs` recognise only a qa-engineer PASS. And the red-test manifest is required only on the bugfix sr-engineer → code-reviewer edge, while on the test-first chain the tests are handed over on qa-engineer → sr-engineer. This ticket makes those checks read the judge's report through one shared resolver, arms the manifest-must-exist check on the qa-engineer → sr-engineer hand-off (skipped when qa-engineer recorded that no new test is needed, ruling 10), and keeps every outcome on an unmarked feature byte-identical. Existence-only semantics are unchanged: the server parses no manifest row and runs no test.

## User Stories

- As a code-reviewer judging a test-first feature, I want my PASS checked against my own report, so that the chain can complete without a qa-engineer report that no longer exists on this path.
- As a human relying on the gates, I want a code-reviewer PASS with no judge report rejected under the existing completion-evidence codes, so that the new path is not weaker than the old one.
- As a coordinator, I want the qa-engineer → sr-engineer hand-off rejected when qa left neither a red-test manifest nor a "no new test" record, so that sr-engineer never builds against tests nobody declared.
- As an integrator / release-engineer, I want `lane-status`, drift and `scripts/release.mjs` to accept a code-reviewer PASS on a test-first feature, so that a lane on the new path can be observed, landed and released.
- As a maintainer of an in-use workspace, I want every unmarked feature to behave byte-for-byte as before, so that `main` keeps working while E433–E435 land.

## Acceptance Criteria

Terms. *Marked* / *unmarked* feature: as in E431 (persisted `chain_path: "test-first"` or not; file mode only). *Resolver*: the single shared function the architecture names that, given a chain path (and task id / feature where needed), returns the judge identity and the judge-report location(s) every check below reads. *Judge report for id X*: the file the resolver names for X on a marked feature (location and section names are the architect's call, see D1). *No-new-test record*: the form ruled under D2 (recommended: the file `qa_reports/no-new-test_<feature>.txt`). All ACs are file mode unless stated. Every `proof:` is a test qa-engineer writes in a new `test/e432-*.test.mjs` file (qa names the file; each test title starts with the AC id); run as `node --test test/e432-*.test.mjs --test-name-pattern "<AC id>:"` from the worktree after `npm run build`. Tests locate the judge report by calling the resolver export, never by restating its path.

- **AC1 (backlog acceptance 1)** — Given a marked feature at `code-reviewer:In_Progress` whose lane ledger holds T1, with `qa_reports/expected-red_<feature>.txt` present, a spec `specs/<feature>.md` carrying ≥1 `proof:` line, and a judge report for T1 that carries both required sections (the expected-red disposition and the AC execution record, D1), when code-reviewer writes `status: "PASS"` with `completed_tasks: ["T1"]`, then the write is accepted and persists `status: PASS`, `last_agent: code-reviewer`.
  proof: `node --test test/e432-*.test.mjs --test-name-pattern "AC1:"`
- **AC2 (backlog acceptance 2, both completion-evidence codes)** — Given the AC1 feature with no judge report for T1, when code-reviewer writes `PASS` with `completed_tasks: ["T1"]` (T1 not yet in the on-disk completed set), then it is rejected `QA_COMPLETION_EVIDENCE_MISSING`, the message names the path the resolver checked, and no state is written. Given instead that T1 is already in the on-disk completed set and no judge report exists, when code-reviewer writes `PASS` with `completed_tasks: ["T1"]`, then it is rejected `MISSING_EVIDENCE` and no state is written.
  proof: `node --test test/e432-*.test.mjs --test-name-pattern "AC2:"`
- **AC3 (expected-red and AC record read the judge report)** — Given the AC1 feature whose judge report for T1 lacks the expected-red disposition section, when code-reviewer writes `PASS`, then it is rejected `EXPECTED_RED_DIFF_MISSING`. Given the judge report lacks the AC execution record section (expected-red section present), when code-reviewer writes `PASS`, then it is rejected `AC_EXECUTION_LOG_MISSING` and the `Inspected:` list names the judge report path. Given a report at the old (qa-engineer) location only, which the resolver does not name for a marked feature, then it does not clear either check (if the architect keeps the same location for both paths, this sentence is vacuous and the test asserts the resolver returns that one location).
  proof: `node --test test/e432-*.test.mjs --test-name-pattern "AC3:"`
- **AC4 (completion evidence on non-PASS judge writes)** — Given a marked feature, when code-reviewer writes `In_Progress` (or `FAIL`) whose `completed_tasks` adds T2 with no judge report for T2, then it is rejected `QA_COMPLETION_EVIDENCE_MISSING`; with the judge report present it is accepted. Given an unmarked feature, when code-reviewer writes non-empty `completed_tasks`, then it is rejected `REVIEWER_COMPLETED_TASKS_REJECTED` with today's text.
  proof: `node --test test/e432-*.test.mjs --test-name-pattern "AC4:"`
- **AC5 (backlog acceptance 3)** — Given a marked feature at `qa-engineer:In_Progress` with no `qa_reports/expected-red_<feature>.txt` and no no-new-test record, when qa-engineer hands to `sr-engineer:In_Progress`, then it is rejected `REPRO_MANIFEST_MISSING`, the message names both the manifest path and the no-new-test record path (Copy msg.qa_to_sr_manifest), and no state is written.

### D2 options — worked example

Two marked features. **e450-readme-typo** (feature ticket): fix a typo in `README.md`; nothing to test. **e451-drift-crash** (bug ticket, `dispatch_mode: bugfix`): `tw_detect_drift` crashes on a corrupt git index that qa cannot reproduce from the public interface without building the corruption by hand, so qa records "no new test" and sr writes the reproduction test (ruling 4).

- **(a) File `qa_reports/no-new-test_<feature>.txt` (recommended).** e450: qa writes `qa_reports/no-new-test_e450-readme-typo.txt` ("docs-only change, no behaviour"), then `tw_update_state(agent_id: qa-engineer, In_Progress → sr-engineer)` → accepted (AC6). sr edits README → code-reviewer → PASS; no manifest, so the expected-red check stays dormant. e451: qa writes `no-new-test_e451-drift-crash.txt` → qa → sr accepted; sr writes the repro test and `expected-red_e451-drift-crash.txt`; sr → code-reviewer (bugfix check, existence only) accepted; at PASS the judge report needs the expected-red disposition. What it costs: one predicate beside `hasExpectedRedManifest`; no schema, no tool-boundary or description change, no count pin. What breaks: nothing in the suite; the file stays at the `qa_reports/` root after release (not archived, Out of Scope); like the manifest, anyone can create it (same trust as every existence check).
- **(b) Persisted handoff field** (e.g. `no_new_test: "<reason>"`, feature-scoped, file mode only). e450: qa writes `tw_update_state(..., no_new_test: "docs-only")` on the qa → sr write → accepted, field visible in `tw_get_state` to sr and code-reviewer. e451: same, sr then writes the manifest. What breaks: handoff schema 16 → 17 with a lazy migration — the 14 pinned files in the plan (`test/schema-versions.test.mjs` … `test/e431-test-first-server-path.test.mjs` AC16) re-pinned, `docs/schema-versions.md`, `tools/registry.ts` input schema + description (`test/e441-tool-description-contracts.test.mjs`, `test/e409-lite-write-tool-facts.test.mjs` likely move), +2 sr tasks (~8 files), the primary MCP server must restart after the merge, and E435 bumps the schema again weeks later. Stale-carry question: a round-1 "no new test" stays on the feature after a code-reviewer rejection asks qa for a missing test (harmless for the OR check, misleading to a reader).
- **(c) Transient field on the qa → sr write only** (not persisted). e450: same write as (b), accepted, nothing persisted. What breaks: no durable record — on e451 code-reviewer cannot see from state or disk why the manifest came from sr rather than qa; still moves `tools/registry.ts` boundary + description tests; no schema bump.
- **(d) A sentinel inside the manifest — rejected.** An empty or comment-only `expected-red_<feature>.txt` would arm `EXPECTED_RED_DIFF_MISSING` at PASS for a ticket with nothing red, and on e451 qa's sentinel manifest would satisfy the bugfix sr → code-reviewer check before sr wrote any repro test, defeating ruling 4.

## tools/lane-migrate.ts

- **Two functions per runner.** A lock-free `*Locked` core runs the whole pre-flight plus move critical section and assumes the caller holds the lane lock; a thin public wrapper takes that lock and calls the core. This mirrors `writeHandoffState` / `writeHandoffStateCore` in `tools/handoff-write.ts`. `withFileLock` is O_EXCL-based and not re-entrant, so a caller that already holds the lane lock (`writeHandoffStateCore`) must call the core; nothing may acquire the same lock path twice on one call stack.
- **Destination lane.** flat->lane targets the branch-based live resolver (`resolveCurrentLane`), not the lane implied by the flat handoff's `active_feature`. The runner never parses the flat handoff, and must not import `tools/handoff-parse.ts`, which imports this module.
- **Lock.** Per-lane, at `.current/<lane>/.handoff.lock`: the destination lane for flat->lane, the source lane for lane->flat. A live writer of the same lane takes the same lockfile, so the migration and that writer serialize.
- **Candidate files.** Derived by iterating the `LANE_FILES` registry, never a second list of filenames. Anything else (`.config.json`, `exemptions.json`, `feature-split.md`, `.current/archive/`) is never read, moved or deleted. An entry marked `noFlatCounterpart` (tasks.md) is never planned: its legacy location is not `.current/<filename>` and its transition belongs to the tasks lane migration. lane->flat refuses while the lane dir still holds tasks.md (run the tasks reverse first).
- **Move, not copy.** `fs.renameSync` is the atomic publish (the source is already complete on disk, so readers see the old or the new path, never a partial file). Bytes are untouched, so a round trip is byte-identical.
- **Refuse, never clobber.** Every check (required entry present, destination conflict, lane-dir purity) runs before the first move. handoff.md at the destination with different bytes throws with both sides untouched; identical bytes is a completed move from an interrupted run, so the redundant source is removed and the entry reported as moved (idempotent resume). Dual presence is reported one layer up as `HANDOFF_LAYOUT_CONFLICT`; the runner's throw is the backstop.
- **Sidecar merge, flat->lane only.** An optional append-only JSONL entry (telemetry/metrics/usage/dispatch.jsonl) already at the lane destination is normal (the usage hook may append to the lane path before the first `tw_*` call migrates the handoff). It is merged, flat lines first, and published atomically inside the same critical section. A lane file that already starts with every flat byte is a published merge whose source removal died; the source is dropped instead of merged again (`isBytePrefix`, the same predicate the read-side aggregation uses to skip half-merged files). The reverse runner keeps refuse-on-different-content for every entry, since a merge cannot be un-merged.
- **Never merged.** An optional entry that is not a `.jsonl` log (today pending-tickets.md) is required-shaped at the destination in both directions: identical bytes drop, different bytes refuse. Concatenating two markdown files would give two "## Applied" sections and duplicate `lane_local_ids`. A future non-JSONL optional entry defaults here, the safe direction.
- **Merge race.** Sidecar appenders (telemetry, metrics, dispatch log, usage hook) append without the handoff lock, so a line appended to the destination after it was read would be lost by the rename. The optimistic re-read before the rename narrows this to the stat->rename gap; it cannot close it.
- **flat->lane core resume cases.** Required entry absent at the source but present in the lane: leftover flat sidecars are swept in via the merge/resume rule; with none left over the caller lost a concurrent race and gets `alreadyMigrated: true` with nothing touched. Absent at both paths with `opts.allowMissingRequired` (set only by the own-workspace triggers in handoff-parse / handoff-write): sidecars move, no throw. A non-JSONL optional entry with different bytes at both ends refuses.
- **lane->flat core.** Tolerable debris is a `.handoff.lock` regular file, a `tasks.md.lock` regular file, or a stale `<lane file>.<pid>.<ms>.tmp`; a debris-named directory is foreign and refuses in pre-flight. Stale tmp files and a stale tasks.md.lock are removed after the moves; the held lock and a live tasks.md.lock never are. Because the held lockfile lives inside the lane dir, the core removes the dir only if already empty, and the public wrapper removes it after release.
- **Out of scope.** The close-time move of a live lane to `.current/history/<YYYY-MM>/<lane>/` is a different operation.

## tools/join-precondition.ts

- **Problem.** Whether a join ticket's `depends_on` is satisfied otherwise lives only as prose ("J1a PASS at <sha>, L3+L4 merged at <sha>") that nothing checks, because the dependency's PASS sits in another workspace's handoff, which this workspace never reads (governance state is workspace-scoped). Two local, cheap checks close the gap without a cross-workspace read: `git merge-base --is-ancestor <lane-branch> HEAD` (answerable from shared local object history), and comparing this workspace's own declared plan (`.current/feature-split.md`) against its own record (`.current/handoff.md`).
- **Invariant.** Zero cross-workspace reads: no exported function takes a second workspace path, and no read or exec is parameterized by anything but `repoRoot`. `tools/feature-rollup.ts` deliberately reads sibling worktrees for an opted-into roll-up; this module is the opposite by design.
- **Membership, not per-row equality.** A Split Table has one row per planned lane, so at most one row can equal this workspace's `active_feature`. The round-1 defect emitted one finding per non-matching row, fabricating a mismatch on every healthy multi-row plan. Rows are never skipped by a `status` column: that would make pass/fail depend on status-column hygiene, a remedy the PM considered and refuted (spec Amendment History).
- **Honest degradation.** No split file, no recognizable identity column, or no readable `active_feature` returns `{ compared: false, reason }`, never a fabricated match or mismatch.
- **Out of scope.** A callable build-entry self-check, not a hard gate in `gates/registry.ts` / `UPDATE_STATE_GATE_PIPELINE`.

## tools/lane-paths.ts

- **Single owner.** Every consumer (`resolveLanePaths`, the two migration runners in `tools/lane-migrate.ts`, the dispatch-log sidecar name) derives its file set by iterating `LANE_FILES`. Adding a lane file is one `LANE_FILES` entry plus a schema migration step (the `tasks` entry is the worked example).
- **Callers.** Every production lane-file call site goes through `resolveCurrentLanePaths`: handoff-parse, handoff-write, drift, telemetry, metrics, dispatch-log, `guards/session.ts`, `prompts/build.ts` and both `bin/` hooks. The flat `.current/<filename>` layout is legacy, reached only through the migration runners and never written by a live writer.
- **fs use.** Pure path and string logic except three read-only functions: `resolveCurrentLane` (stat / read on `.git` and HEAD), `enumerateLaneSidecarSources` (readdir / read over `.current/`) and `hasHistoryLedger` (readdir / stat over `.current/history/`). Never a git subprocess (the `tools/drift.ts` precedent), never a write, no imports beyond `fs` and `path`.
- **Registry entries.** `pendingTickets`: a lane's filed-but-unnumbered findings (format parsed by `tools/lane-ticket-allocation.ts`), applied to `docs/backlog.md` by `agc feature finish`. `required: false` is load-bearing: a lane that files no finding has no such file, and a required entry would make every ordinary lane->flat migration refuse. It is committed markdown, so it is never concatenate-merged. (E179) `tasks`: the lane-local ledger `.current/<lane>/tasks.md`; optional (a lane with no tasks has none) and `noFlatCounterpart`, because its legacy location is the taskPaths-resolved root file, not `.current/tasks.md`. (E125a) `baseSha`: `.current/<lane>/base-sha`, the fork-point commit `agc feature start` resolved, read back by `agc feature finish --shipped` for the `lane_closed:` pointer line. It must be registered, since an unregistered file in the lane dir makes the lane->flat runner refuse the lane; optional and non-JSONL like pendingTickets (identical bytes drop, different bytes refuse), and deliberately without `noFlatCounterpart`, since no other module owns its flat<->lane transition. (E125b)
- **TICKET_ID_RE.** Letters, exactly one mandatory digit, then `[a-z0-9]*`, terminated by `-` or end of string. Writing `\d+[a-z0-9]*` would let two adjacent quantifiers both claim a digit run, so a long unterminated digit string backtracks quadratically. The accepted language and the capture are identical (both greedy, anchored by `(?:-|$)`). Shared by `resolveLaneName` and the live resolver.
- **resolveLaneName.** Kept exported for "what lane would this active_feature imply" lookups. It must never return `_primary`: branch-based resolution and its PRIMARY_LANE fallback belong to the live resolver only.
- **Lock path.** `resolveLaneLockPath` is used by the migration runners for the migration's lane and by `tools/handoff-write.ts` for the current branch's lane, so both serialize on the same file. `withFileLock` creates the lock's parent before its O_EXCL open.
- **Sidecar dedup (`enumerateLaneSidecarSources`).** Sources: live `.current/<lane>/<file>` for each safe lane dir outside `NON_LANE_DIRS`; history `.current/history/<YYYY-MM>/<lane>/<file>` (two buckets with the same lane name are distinct closures, both kept); the legacy flat file. Dedup never goes by name alone, because a long-lived lane such as `_primary` keeps its live dir and its history dirs. A history copy of lane L is skipped iff it is a byte prefix of live L (caught mid-move). The flat file is skipped iff it is a byte prefix of some counted lane copy, live first then history: the shape an interrupted `mergeSidecar` leaves (`flat ++ lane` published at the lane path, flat not yet unlinked). Any lane is checked, not only the current branch's, since the branch may have changed and the lane may have closed into history. Empty files are never skipped. An unlistable dir or unreadable file is simply not a source.

## tools/lane-registry.ts

- **Why a module.** Moves `localFallbackLaneList` (`tools/feature-rollup.ts`) behind a module serving two consumers with very different cost profiles: the feature roll-up wants feature-history attribution and can afford a per-lane history scan (occasional, human-invoked); `tw_get_state` is the hottest read in the server and must never pay for a ticket-list read or history scan just to answer "who else is working, and on what".
- **Not a written registry.** A written registry brings back a shared write target, exactly what per-lane state directories exist to avoid, and goes stale when a lane dies without cleaning up. A derived list has no stored copy to drift. The module performs no writes, creates no lockfile, sends no heartbeat.
- **Degrade honestly.** An unreadable or unattributable lane is always carried, never dropped or zero-filled; every degradation states a reason; a partial figure is never presented as a verified total.
- **Import cycle.** `tools/handoff-parse.ts` -> this module (`getLaneRegistrySummary`) -> `tools/feature-rollup.ts` (`localFallbackLaneList`) -> `tools/handoff-parse.ts` (`parseHandoff`). Same shape, on three nodes, as the documented handoff-parse <-> handoff-write cycle. Safe because every cross-edge is a function call made at runtime inside a function body, never read at module-init time, so ESM live bindings resolve it whichever module loads first.
- **Feature history ordering.** Entries are the exact (unsanitized) `active_feature` / metrics `feature` strings, one list oldest to newest by each source's own timestamp (handoff `last_updated`, metrics row `ts`), never file mtime (a checkout gives every file the same mtime). Metrics rows matter because a long-lived lane such as `_primary` changes `active_feature` in place and never closes into history; each shipped close (`emitFeatureMetrics`) leaves a durable row recovering the superseded predecessors. Within one lane dir a feature appears at most once (the handoff entry wins; repeated metrics rows collapse to the earliest); separate lane dirs are never merged. A missing timestamp sorts last; ties break by lane name, then path. The flat-era `.current/archive/` is no longer read.
- **Known limitation.** An abandoned feature (no shipped close, so no metrics row) later overwritten in place by a new `active_feature` cannot be recovered; metrics.jsonl records shipped closes only, and the module never claims data that was not durably recorded.
- **Summary cost ceiling.** `getLaneRegistrySummary` skips the history scan because every lane on this path pays for every sibling's extra I/O on every read. `timeoutMs` defaults to 200, a fixed production constant (same posture as `STALE_DISPATCH_THRESHOLD_MIN` / `HOP_CAP`, never config-driven), exposed only for tests. It bounds only the `git worktree list` subprocess; the N synchronous sibling `parseHandoff` reads that follow are additive. The try/catch is defense in depth, so this function is never the reason the mandatory first-action read fails.

## tools/lane-status.ts

- **Why.** Replaces the integrator's by-hand lane read (per-worktree handoff reads, `git log` / `git status` per lane, adding hop and round counts against caps, eyeballing claimed completed_tasks against on-disk qa evidence). Wave 5 showed every one of those failing by hand.
- **Reporting surface only.** Like `tools/feature-rollup.ts` it fires no gate, writes nothing, and never makes a cap span workspaces (the server is deliberately workspace-scoped). (E109)
- **Data sources (all imported, none modified).** Lane list: `laneRegistryList` in `tools/lane-registry.ts` (itself `git worktree list` via feature-rollup), never a `specs/fanout-*.md` manifest, which is the manifest module's job. Handoff round fields: `parseHandoff` (LaneInfo carries hop but not review/qa rounds). Same-feature hop/ticket totals: `computeFeatureRollup`, fed this module's lane list so nothing is re-derived. Caps: `HOP_CAP_EXPORTED` / `ROUND_CAP_EXPORTED` / `REVIEW_ROUND_CAP_EXPORTED` from `tools/transitions.ts`, never a hardcoded number. Evidence: `parseCoversIds` from `tools/evidence-file.ts` plus direct `review_<id>.md` filenames, PASS rounds only. Ticket token and lane ledger location: `resolveLaneName` / `LEGACY_LANE` / `PRIMARY_LANE` / `isSafeLaneName` / `laneFile`, never a restated ticket-id regex. Deliberately not the lane-path resolver functions: each has its own pinned caller allow-list in the lane-path tests, and the row's branch already names the lane.
- **Watch mode.** `runLaneWatch` is a polling event stream over every lane's handoff state for the integrator's Monitor tool, following the mailbox watch script's baseline / `expiring — re-arm` / exit-code conventions. Each tick reads only the lane list and each lane's handoff (no git log/status, no evidence cross-check), so a tick stays cheap. It never exits on the first change; at expiry the re-arm command carries the fingerprint of every lane's state line as this watch last read it, never a fresh read, so a transition landing between two watches still fires as `changed since last watch:`. Read-only, no watch lock. (E178b)
- **Degrade honestly.** A lane whose handoff is missing or unparseable is carried with `readable: false` and a reason, never dropped or zero-filled, and the whole report is marked degraded with a stated reason.
- **Evidence cross-check filters (`checkLaneEvidence`).** The same filters apply to `qa_reports/` and `qa_reports/archive/<feature>/`; neither is scanned unfiltered. PASS-only: a file with no `— PASS — by qa-engineer` round contributes nothing. In scope: the id is in completed_tasks, or carries the feature's ticket token as a delimited segment (`e177b-lane-status-tooling` -> `e177b` -> `T-E177B-04` in scope, `T-E125A-01` not), because a worktree's `qa_reports/` holds every merged feature's evidence and a release archive a whole wave's. No token: scoping falls back to completed_tasks membership and the report says so (`TOKEN_NOT_DERIVABLE_NOTE`). Voided: an id voided in the lane's own tasks ledger never counts; `lane` names that ledger, and computeLaneStatus passes the branch's lane (`feat/<id>-*` -> id, else PRIMARY_LANE, mirroring the live resolver); omitted, it defaults to the feature's ticket token, else PRIMARY_LANE.

## tools/stale-notify.ts

- **Why.** The stale_dispatch advisory (computed in `tools/handoff-parse.ts` at `tw_get_state` time) is pull-only, so nobody sees it until the next session reads state, and a long idle window can go unnoticed. This module is the cheapest push channel. Opt-in example: `{ "staleDispatchNotifyFile": ".current/stale-dispatch.notify" }`.
- **Watch-file emit only.** An external watcher (fswatch / inotifywait / launchd -> desktop notification, webhook, anything) turns the mtime bump into an alert. The server spawns no daemon or timer thread and owns no delivery mechanism.
- **Semantics.** Key absent (the default): fully disarmed, null return, no behaviour change, opt-in per workspace like the exemptions / auto-tier keys. One emit per distinct stale dispatch: the prior file is read back and the emit is skipped when its (dispatched_at, role) pair matches, so a watcher fires once per threshold crossing rather than on every `tw_get_state` of the same stale window. The watch-file itself carries this dedupe cursor (no new handoff state); a fresh dispatched_at re-arms naturally. Payload: advisory fields + workspace + emitted_at, pretty-printed JSON, published tmp + rename (the atomicWriteConfig convention) so a watcher never reads a torn file. Not schema-versioned: a transient signal file, not governance state.
- **Never throws** (the `tools/exemptions.ts` posture). It sits on the mandatory first-action read path, so every failure (unreadable config, unwritable path, corrupt prior file) collapses to a loud `error` string the caller surfaces inside the stale_dispatch payload. File-mode read path only.

## tools/merge-invariants.ts

- **Why.** `tw_detect_drift` compares two views of one workspace's current state, so a merge that drops a lane's task rows and their [x] marks symmetrically reads as "no drift". This module checks the merge commit itself. Spec: `specs/e126-merge-invariants.md` (AC1 task ids, AC2 [x] marks, AC3 sidecar counts).
- **Git trees only.** Every tree is read through `git ls-tree` / `git cat-file`, never the working directory, so any already-made merge commit can be checked. It touches no git state.

## tools/metrics.ts

- **Separate stream.** Fully separate from the gate-fire telemetry stream in `tools/telemetry.ts`: disjoint key sets, writers and lifecycles, like the usage / telemetry split. Observability rather than authoritative state, so it is deliberately not governed by the handoff 4-step mutating-tool contract. (E8)
- **Round semantics.** The definition is in `specs/e8-success-telemetry.md`, and the counters this module reads (`computeNewRound` in `tools/transitions.ts`) implement it exactly: a round that ends APPROVED or PASS increments nothing. The terminal round must not be folded in for two reasons: `one_pass` is defined as all three being 0, so counting it would make one_pass permanently false and destroy the record's headline metric; and this emit site never sees a verdict (`emitFeatureMetrics` receives only the three totals), so it cannot tell an APPROVED close from any other. A rounds-run signal, if wanted, belongs in new fields alongside these. (E52, E85)

## tools/lane-ticket-allocation.ts

- **Problem.** Two lanes forked from the same base both read "max is E176" and both mint E177; each lane appends its own backlog row, so the collision is invisible to a textual `git merge`. The remedy is structural: a lane never picks a real id. It files a candidate under a lane-local token (`<LANE>-NEW-n`) in `.current/<lane>/pending-tickets.md`, and a single writer later allocates real ids in one sequential apply that observes the previous apply's result. Collision-freedom follows from that single-writer discipline, which this module assumes but does not enforce. Spec: `specs/e124-lane-ticket-allocation.md`.
- **Pure by construction.** No `fs`, no `child_process`, no clock, no environment read. Reading the pending file (or `git show <branch>:<path>` for an orphaned branch), reading `docs/backlog.md`, enumerating worktrees and branches, and writing results back are explicit arguments or return values owned by the caller (the `agc feature` CLI).
- **File format.** Ordinary markdown; only fenced blocks whose info string is exactly `pending-ticket` carry data, so prose around them is ignored. Fields: `lane_local_id` (e.g. `L-STATE-NEW-3`), `title`, `priority`, `depends_on` (a list mixing real ids and lane-local tokens), optional `source`, optional `body` (a YAML block scalar of free prose). A block never carries an `id` field: the real id is the allocator's to assign. Blocks under a `## Applied` heading are the archive `markApplied` maintains, kept verbatim and never returned by `parsePendingTickets`, so "has at least one unapplied entry" (the orphan check's input) is a checkable fact rather than "the file exists".
- **Degrade honestly** (the `tools/lane-registry.ts` posture). One malformed block is skipped and reported, never allowed to take its siblings down; an unresolvable dependency is surfaced, never dropped and never left as a dangling lane-local token inside a shipped backlog row.
- **Scanner.** Tracks fenced-code state so that a heading or a `pending-ticket` fence quoted inside another fenced block (a markdown example of the format) is not live structure, and a `pending-ticket` block's own content can contain `## Applied` or a shorter fence. Closing fences follow CommonMark: a backtick run at least as long as the opener's. A `pending-ticket` opener seen while a non-pending fence is open is recorded; when that fence closes, each one whose run is >= the fence's is reported as `closes-enclosing-fence` (under CommonMark its closer necessarily ended the outer fence, so it can never be legitimately nested), and one with a strictly shorter run is legal nesting (a documentation example) and is dropped silently. If the fence is still open at EOF, every one is reported as `unclosed-at-eof`.
- **Parse rejections.** A block is skipped and reported when it is unclosed, is not a YAML mapping, lacks a non-empty string `lane_local_id`, `title` or `priority`, carries an `id` field, uses an `E<n>`-shaped `lane_local_id` (indistinguishable from a real id in `depends_on`), has a malformed `depends_on` / `source` / `body`, or repeats a `lane_local_id` taken by an earlier block in the same file. With `opts.appliedLaneLocalIds`, a well-formed archived block whose `lane_local_id` has no provenance row in the backlog is reported too (a finding written below `## Applied` that would never be allocated); an archived block that fails validation is never reported.
- **Allocation order and dependencies.** Ids are assigned batches in array order and entries within a batch in array order (AC3), deterministically; any cross-lane ordering policy is the caller's. Dependencies (AC4) resolve after every id in the call is known, so a forward reference resolves too. Per reference: an `E<n>`-shaped id (sub-letters allowed) passes through unchanged; a lane-local token is rewritten to the allocated id of the entry with that `laneLocalId`, looked up in the dependent's own batch first and then across all other batches, provided exactly one match exists at the first level that has any. Zero matches, an ambiguous match or a self-reference is reported in `unresolvedDependencies` and left out of the ticket's `dependsOn` and `backlogRow`. Resolved ids are de-duplicated, first occurrence wins.
- **Collision-freedom (AC5).** A second call whose `currentMaxId` is re-derived from the backlog after the first call's rows land (equivalently, the first call's `maxAllocatedId`) starts strictly above every id the first call issued. No disposition parameter: shipped and abandoned lanes apply identically (AC9). A bad `currentMaxId` throws because an allocator that guesses a base would reintroduce the very collision this module prevents.
- **Max id.** A sub-lettered split counts by its base (`E174a` -> 174, `E9A` -> 9); ignoring it would undercount the true max, and an undercount is exactly the collision to prevent. An id in a later cell or in prose never counts.
- **Provenance lookup.** Only lines whose leading cell is an `E<n>` id are scanned, so prose, fenced examples and tables without an id column never match. The lane is compared as `formatBacklogRow` plus the row's cell transform would have written it, and `e17` never matches `e179`.
- **Orphan lanes.** `hasUnappliedPendingTickets` is computed over the COMMITTED `.current/<lane>/pending-tickets.md` of the branch's own lane only (`feat/e179-x` -> `e179`; a branch resolving to no lane is not a candidate). Another lane's file the branch happens to carry (forked from base between that lane's merge and its finish) is never consulted. Mere existence is not enough: `markApplied` leaves the file in place with its entries archived, so existence would report an already-applied lane as an orphan forever. Branch names are compared against branch names, never against lane names.
- **markApplied.** Fences and payload move byte for byte. Re-parsing the result no longer returns the moved entries; every other entry, all prose, and every block `parsePendingTickets` would skip as malformed stay where they were. The blank line taken with a moved block avoids leaving a doubled blank-line gap. When nothing matches, the input is returned unchanged. No disposition parameter (AC9).

## tools/tasks-lane-migrate.ts

- **Two forward shapes.** `_primary`: copy the legacy body into the lane ledger, then re-stamp the legacy file as a v2 index (sentinel + notice + body) and write the reverse-run receipt `.current/tasks-index-receipt.json`. Feat lane: move every `## ` section whose heading's ticket id is the lane into the lane ledger; each contiguous run becomes one marker line in the legacy file, whose sentinel is left untouched.
- **Index, never a source.** A legacy file at v2+ is an index, never a forward source, but a missing ledger it proves must exist is reported loudly (TasksLedgerAbsentError), never treated as empty. A git-ignored lane path skips the migration and keeps the legacy file as the ledger.
- **Locks.** The lane's tasks lock is OUTER, the legacy file's lock INNER. Both are taken with a small synchronous bounded-wait lock whose timeout throws TasksMigrationBusyError, never a silent skip.
- **Reverse.** Runner-only, no CLI: `migratePrimaryReverse` and `migrateFeatReverse` restore the legacy file from the lane ledger's CURRENT body and delete the ledger. Every precondition is checked before the first write, so a refused run touches nothing.
- **Core caller contract.** `laneTasksPath` is resolved once by the caller (the four `tools/tasks-file.ts` mutators, via withFileLock), so the lock held and the ledger written can never diverge; the lane is that path's parent directory name. This deviates from the blueprint's `(ws, lane)` signature because spec AC1 routes every tools/ caller through the current-lane path resolver. No-op cases: the lane ledger exists, no legacy file exists, the lane path is git-ignored (AC4b), or there is nothing to move (D13).
- **`_primary` reverse receipt check.** The receipt's bodySha256 must equal `primaryIndexReceiptSha` of the index's trailing body, or, for a receipt stamped before index normalization existed, sha256 of that raw body. A missing or unreadable receipt refuses. Normalization allows exactly two root edits after the forward run: removed `tasks_moved` markers and a `## Closed Lanes` section; any other change refuses. The restored body is the ledger's current body minus the ledger marker lines no longer in the root, with the root's Closed Lanes section(s) carried to the end in place of the ledger's own; with no Closed Lanes section on either side the ledger body is kept verbatim. The restored root always carries a v1 sentinel, so a v0 (sentinel-less) original such as the `agc init` scaffold round-trips to its body under a v1 sentinel, not byte-identically. (E125c, E195)
- **Feat reverse markers.** A missing LAST marker refuses too, which is why every marker carries the run total `of=<N>` (C2). Leftover content (sections added lane-locally) goes right after the last marker's run, or at the end of the file when there are no markers (spec D-E).

## tools/tasks-file.ts

- **Two halves of the line-terminator defence.** The input-boundary guard (`containsLineBreak`) only covers the tw_* RPC path; a tasks.md edited by hand, the most likely real trigger, never passes through a mutator, so the parser itself must not let a terminator-corrupted row disappear silently. `TASK_LINE_SHAPE_RE` is a loose, terminator-tolerant recogniser for "this looks like a checkbox task row" (open `[ ]` or done `[x]`) that, unlike the configured taskPattern, need not reach `$`: the checkbox marker and the start of the id token both come before any U+2028/U+2029 in a note or reason suffix. It is scoped to the DEFAULT_TASK_REGEX row shape; there is no generic way to detect "matches an arbitrary custom pattern except for the terminator", so for a custom taskPattern the input-boundary guard remains the main defence. (E131)
- **Why a corrupted row must fail loud.** The row really is on disk (`split("\n")` never breaks on U+2028/U+2029), but the strict regex's trailing `(.+)$` cannot cross the terminator, so without the throw it would vanish from parseTasksFromFile, getNextTask, tw_detect_drift and tw_sync at once with no signal anywhere.
- **Input-boundary refusal.** Every mutator embeds a caller-supplied string into a task line (via a replacer function, or plain concatenation in addTaskInFile). A value containing CR or LF plants an independently parseable line elsewhere in the file (a forged task row), which voidTaskInFile's post-write check cannot see because it defends `taskId` only, and the sibling mutators cannot see at all. U+2028/U+2029 are line terminators for JS regexes (`.` cannot consume them, an un-anchored `$` cannot cross them) but not for `split("\n")`, so such a row stays in tasks.md yet vanishes from every reader. One widened character class covers both failures: CR/LF forges rows, U+2028/U+2029 erases them. A loud refusal beats silently flattening text the caller typed. (E121, E131)
- **Void marker.** `-` is outside DEFAULT_TASK_REGEX's `[ x]` class (and any custom taskPattern following the same "space or x" convention), so a voided line is invisible to parseTaskLine and every consumer: getNextTaskFromFile never offers it again, tw_detect_drift never counts it as completed, incomplete or drift, and tw_sync never treats it as a reconcile candidate. (E117)
- **No re-cut of a voided id.** `review_reports/review_<id>.md` and `qa_reports/review_<id>.md` are existence-based and keyed only by id, so a re-cut would silently inherit the voided task's review and QA evidence and pass both gates for work nobody reviewed. addTaskInFile scans for the fixed `- [-] <id>` format directly and refuses: a re-cut is different work, and refusing removes the problem state instead of adding a version field every future evidence reader would have to honour. The marker line itself stays on disk. (E120)
- **Only open rows may be voided.** Completion is checked against both the tasks.md mirror and `handoff.completed_tasks`: tasks.md can lag the ledger (the state tw_sync repairs), and voiding in that window would delete the row a completion check depends on, making the drift permanently unreachable (`tools/drift.ts` builds its id vocabulary from tasks.md alone). An already-voided id is reported differently from one that never existed, since the marker line is still on disk.
- **Post-write invariant.** Asserted against the real content about to be written, not a hand-rebuilt line (which can miss both a newline and a `$`-expansion escape): the candidate is produced by the same `String.replace` call as the write, then re-parsed line by line, as parseTasks does, against the workspace's configured taskPattern. A custom taskPattern with a different completion convention could otherwise accept the write and report success while the row keeps being offered. The check compares `parsed.id === taskId` only, so a different forged id (from a newline-bearing reason) would pass it; the boundary guard closes that. What it still catches is a same-id resurrection needing no newline, e.g. a checkmark class that also matches `-`.
- **Matching details for the void-marker scans.** Every scan trims each line before matching (the duplicate-id re-scan, parseTasks), so an indented voided row is supported everywhere; the void scans test the anchored pattern against `line.trim()`, which also strips non-ASCII whitespace (U+00A0, U+2000-U+200A, U+3000, U+FEFF) a `[ \t]*` prefix would miss. The id is bounded by `(?=\s|$)`, not `\b`, because `\b` needs a word character on the id's trailing side and fails for ids ending in punctuation (`T-1.`, `T-1)`) that still match the row's `(\S+)` id group.
- **addTaskInFile taskId guard.** Earlier only `description` was guarded; a newline-bearing `taskId` passed the duplicate-id scan (which compares against the newline-bearing id and never matches), and the planted LF left `- [ ] <taskId-prefix>` descriptionless, so taskPattern's `\s+(.+)$` could not match and the caller's own row was silently dropped. This site never resolves `taskId` against an existing row before writing, so it has no incidental lookup-failure safety net.

The gates that use them read the incoming write args or are file-mode only, so no DDL change was needed and the sqlite schema_version is unchanged. The body never inspects the first argument's shape; the dispatcher above packs positional args first. (E36)
- **Void guard against the ledger.** `existing.completed` is the tasks table's own flag, the SQLite equivalent of the tasks.md checkbox. `handoff.completed_tasks` is authoritative (per `tools/sync.ts` and `tools/drift.ts`), and a row can be `completed = 0` while the ledger already lists it done. Because voiding DELETEs the row, a guard on the table flag alone would turn that stale state into an unrecoverable one. (E117)

## tools/registry.ts

- **Registry pattern.** Before it, every tool had three independent registration sites (JSON Schema literal, zod const, dispatcher case) and every prompt two (metadata array, if-chain). Do NOT move this file to a top-level `registry/` directory: `test/error-code-contract.test.mjs` globs `tools/` for its code source files (AC-7 of the registry refactor).
- **Trailing tag-fragment predicate: why tail position alone is not enough.** agc's own documentation dialect routinely ends sentences on a bare `<placeholder>` token (`<role>`, `<feature>`, `<task-id>`, `<field>`, and a byte-verbatim line of `content/coord-01-core-head.md` ending `<which fired>`), and TypeScript prose does the same (`Promise<void>`, `Array<string>`). So the predicate requires both tail position and a genuine tool-call signal, an attribute assignment or a close-tag slash, which neither a placeholder nor a TS generic carries. The same fragment quoted mid-string, with prose after it, is ordinary prose and must be accepted. Example bleed-ins: `<parameter name="pending_notes">`, `</scope_decision_why></invoke>`. (E86)
- **Implementation.** Find the LAST `<` in the trimmed value; everything from there to the end must be consumed by a tag-shaped fragment (open or close, complete with `>` or truncated mid-attribute) that carries the signal. The attribute-value alternative has two halves and only one has to force the tail. The terminated half (`"[^"]*"`) matches a complete value; prose after it would already have pushed the `<` out of tail position, and the outer `\s*\/?>?$` anchor enforces the tail. The unterminated half (`"[^"\s]*$`), firing when the closing quote is missing, must enforce the tail itself: a greedy `[^"]*` would swallow everything to the end including spaces and further sentences, so a mid-string `<parameter name="pending_notes and then more sentences...` would be wrongly rejected. Excluding whitespace from the truncated value means later prose cannot be absorbed.
- **Known gaps, accepted.** A bare open tag with no attribute or slash (`<parameter>`, `<invoke>`, `<function_calls>`), a truncated attribute name with no `=` yet (`<parameter name`), a self-closing tag with no attribute (`<br/>`), and a single-quoted attribute (`<parameter name='x'>`). These look exactly like a bare placeholder without a tag-name vocabulary check, which the design deliberately avoids; leaving them uncaught is the price of never flagging ordinary prose. Spec: `specs/e92-e86-handoff-write-boundary.md`.
- **Handoff arg field notes.** dispatch_pins values are deliberately not a closed enum: the model-tier vocabulary evolves independently, and a typo'd model name is a client-side error the server does not gate on (the same trust class as scope_decision_why). dispatch_mode never gates a transition edge itself; "bugfix" only arms the repro-first check on the fix-phase edge. The two attested booleans (lease_override, bookkeeping_write) apply to this write only, like next_role / resume_of / review_verdict and unlike the durable cut_approved / dispatch_mode; SQLite mode ignores both. review_task_ids has the same shape and limits as completed_tasks and follows the transient, write-scoped protocol-field convention; the old "every open task" fan-out fallback was deleted after an incident (D8).
- **Embedding-model allowlist.** A client passing `embedding_model: "attacker/evil-model"` would otherwise download a crafted `.onnx` from the HF Hub. Adding a model: a PR amending the set plus spot-checking the `.onnx` provenance (HF commit history and Xenova-org membership). Full reachability trace: `research/xenova-reachability.md`.
- **PROMPT_REGISTRY.** Replaces the old metadata array and the 11-branch if-chain. The frozen order and descriptions keep `prompts/list` byte-identical to the pre-refactor output (AC-4); the `teamwork` / `teamwork-lite` ids map to the coordinator skill files. Entries are declarative (C6 DR-2).

## tools/sync.ts

- **Why it exists.** Background or parallel subagents and inline-coordinator execution can leave tasks.md `[x]` checkboxes out of sync with the handoff ledger (a prior visual rollout recorded T18-T35 completed in the handoff while tasks.md T01-T26 stayed unflipped). The state machine assumes sequential single-context handoffs; this op is the sanctioned reconcile for the drift those modes produce. (R10, v3.26.0)
- **Safety.** Promoting a tasks.md-only `[x]` into completed_tasks would bypass the qa-only PASS path, so such rows (vibe-coding drift) are reported, never reconciled. Every id it flips is already in handoff.completed_tasks, which only a qa-authorized PASS path can populate, so tw_sync cannot create a completion that was not already recorded.

## tools/transitions.ts

- **Handler-side union members.** SOURCE_CREDIBILITY_UNVERIFIED is storage-mode-agnostic because it reads `design/<feature>.md`, not handoff YAML, unlike EXTERNAL_REFS_UNRESOLVED / CUT_APPROVAL_REQUIRED. FEATURE_LEASE_HELD fires when the incumbent feature's status is not PASS and its last_updated is within LEASE_TTL_MIN; it reads only the three universal fields, so it works in both storage modes. Like the other handler-side members, they are in the union for handler-side narrowing and envelope consistency, never produced by validateTransition.
- **qa-engineer:Blocked -> pm.** The six peer rows (researcher, design-auditor, pm, architect, sr-engineer, code-reviewer) all have Blocked -> pm:In_Progress, and qa-engineer:FAIL already has a pm escape. `content/skill-qa-engineer.md` routes spec-defect situations (copy coverage gap, visual token coverage gap) via FAIL -> pm, unchanged. This edge covers QA choosing Blocked instead, e.g. "## Visual Structural Assertions" rows that assert a superseded design source after a human-approved divergence: marking pass would write a falsehood into the evidence trail, marking fail would blame an implementation doing exactly what was approved, and FAIL also charges the qa_round budget for a contract defect. From Blocked, PM must be reachable, or the PM amendment would be recorded on a qa-engineer write, muddying who changed the spec. resume_of gates only the PM return leg (pm, In_Progress) -> {code-reviewer, qa-engineer}; requiring it on this outbound edge would make qa-engineer:Blocked differ from its peers and from the FAIL -> pm edge it mirrors. (E45)
- **release-engineer:Blocked.** Most of skill-release-engineer.md's Blocked rows (and its step 7a guard) resolve to a human: a halt resumed via the self-loop, or handed to pm for recovery. The `npm test` regression row names qa-engineer, not pm, so pm alone would be the wrong destination set. Self and pm follow the peer :Blocked keys' shape; qa-engineer follows the qa-engineer:Blocked -> sr-engineer pattern of routing to the role that must fix. (E53)
- **validateTransition precedence.** 1 agent_id required when next.status is non-null; 2 round-cap override (qa_round >= 4 -> only (pm, In_Progress)); 2.5 hop-cap override (hop_count >= 10 on a counted role transition -> only the (pm, In_Progress) landing); 3 self-loop fast path on same-agent In_Progress->In_Progress or Blocked->Blocked; 3.5 Amend-Resume edge pm:In_Progress -> {code-reviewer, qa-engineer}:In_Progress iff next_resume_of names that role (v7); 4 table lookup.
- **Hop cap.** The fourth round-style override. Self-loops and same-agent status changes are not role transitions, so they fall through and are never hop-blocked (DR-9). Only an active_feature change resets hop_count (AC-3, DR-6). (v9, d2-server-brake-accounting)
- **Self-loop pairs.** Blocked->Blocked lets a same-agent Blocked record correct itself (e.g. a malformed Blocked payload) without misstating its status. PASS is terminal by design (a qa-engineer PASS->PASS "correction" must be rejected), and a wildcard would also silently open FAIL->FAIL. (E128)
- **Amend-Resume.** Legacy `resume_of: <role>` pending_notes lines are neither honoured nor rejected (DR-2). "Was actually stranded" has the trust class of scope_decision_why. Rewired onto the structured field by c9-protocol-fields AC-4.
- **computeNewRound table.**
  - qa_round: (qa-engineer, FAIL) -> prev + 1; (qa-engineer, PASS) -> 0; (pm, In_Progress) -> 0; else prev.
  - review_round: (code-reviewer, FAIL) -> prev + 1; (qa-engineer, In_Progress) when prev was (code-reviewer, In_Progress) -> 0; (pm, In_Progress) -> 0; else prev.
  - visual_round (v3.14.0): (qa-engineer, FAIL) with a `visual_fail:` pending note -> prev + 1 (distinguishes pixel/widget drift from a test-logic FAIL); (qa-engineer, PASS) -> 0; (pm, In_Progress) -> 0; else prev.
  - hop_count (handoff v9): feature_changed -> base 0 (the ONLY reset; (pm, In_Progress) does not reset it); role transition (next.agent !== prev.agent) -> base + 1; else base. (D2)
  - qa_rounds_total / review_rounds_total / visual_rounds_total (handoff v12): cumulative mirrors that tick with their per-cycle counter's FAIL branch (the FAIL predicates are copied verbatim so they can never diverge on which event counts), and never reset except on feature change: not on QA PASS, not on (pm, In_Progress) re-entry. (E8)

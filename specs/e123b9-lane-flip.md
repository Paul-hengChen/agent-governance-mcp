# e123b9-lane-flip

E123 F1, stage **J2**: the irreversible flip. v4.0.0 Wave 4. Split: `.current/feature-split.md` row 1.9. Decisions: that file's Decisions section (D1/D2/D3), plus the three cut decisions below (**decided by the human 2026-09-23** — all three on the coordinator's recommended option) which settle the remaining open half of D1 and the two J1-NEW-1 questions. **Decision 1 (AC2) modifies D1** of `.current/feature-split.md` — recorded here for the coordinator to carry back into that file; this spec does not edit `feature-split.md` itself.

## Problem Statement

J1 (`e123b8-flip-prep`) made every lane-file call site route through the resolver and fixed every hazard that would turn wrong the moment the resolver goes lane-aware, but `resolveLanePaths` itself still returns flat `.current/<filename>` paths for every lane argument — the seam is frozen, not flipped. Nothing on disk has moved yet, and the migration runners J1's predecessor (`e123a-lane-layout-migration`) shipped are exported but wired to nothing. This ticket flips the seam, wires the migration to run exactly once per workspace with no window for two callers to race it, decides the two path questions J1 explicitly deferred (lock location, archive location), re-points E132's cross-lane history reader at the new layout, and proves the whole thing is reversible against this repo's own real flat `.current/`. After this ticket merges, the flat layout is legacy: read only through the migration path, never written again (docs/v4.0.0-execution-plan.md §1.3).

## User Stories

- As an sr-engineer working a ticket in a lane worktree, I want my lane's governance files under `.current/<my-lane>/` (not mixed flat with every other lane that ever ran there), so that a worktree can host more than one ticket over its life without one lane's history silently overwriting another's.
- As a workspace that still has last release's flat `handoff.md` on disk, I want the first `tw_get_state`/`tw_update_state` call to migrate it into the right lane automatically, so that no operator has to run a manual migration step before working.
- As two concurrent callers hitting the same unmigrated workspace, I want the migration to run exactly once and neither of us to lose a write, so that the flip is safe under the same concurrency this server already promises for ordinary writes.

## Acceptance Criteria

- **AC1** — `resolveLanePaths(workspacePath, lane)` in `tools/lane-paths.ts` stops ignoring `lane` and returns `path.join(workspacePath, ".current", lane, entry.filename)` for every `LANE_FILES` entry (handoff/telemetry/metrics/usage/dispatch), still derived by iterating the registry — no filename is restated (AC15 lineage, unchanged). `resolveCurrentLanePaths` is unchanged in shape (`resolveLanePaths(ws, resolveCurrentLane(ws))`) and now returns genuinely lane-scoped paths for every already-sanctioned caller (guards/session.ts, tools/drift.ts, tools/handoff-{parse,write}.ts, tools/metrics.ts, tools/telemetry.ts, tools/dispatch-log.ts, prompts/build.ts, both `bin/agent-governance-*.mjs` hooks) with zero new call sites required at any of them.
  proof: `resolveLanePaths(ws, "e123b9").handoffPath === path.join(ws, ".current", "e123b9", "handoff.md")`, extended across all five LANE_FILES keys.

- **AC2 (Decision 1 — migration target lane — decided 2026-09-23: `resolveCurrentLane(ws)`)** — `migrateFlatToLane` in `tools/lane-migrate.ts` derives its destination lane from `resolveCurrentLane(workspacePath)` (the branch-based live resolver), **not** `resolveLaneName(parsed-flat-handoff.active_feature)` as originally coded. **This modifies D1 of `.current/feature-split.md`** (D1's first rung, the explicit-config-key path, is untouched — E73's job; this changes D1's *fallback* rung from "ticket id parsed from `active_feature`" to "the branch-based live resolver"). Coordinator carries this correction back into `feature-split.md`'s D1 row; this spec does not edit that file. `resolveLaneName` stays exported and used only by the still-supported flat-`active_feature`-lookup path (kept for D1's original wording / any caller that still needs "what lane would this active_feature imply", none currently production).
  proof: a fixture where a flat handoff's `active_feature` names a different ticket than the checked-out `feat/<id>-*` branch — the migrated lane directory name matches the branch, not the stale `active_feature`.

- **AC3 (where it triggers)** — The flat→lane migration is invoked lazily, **only from the own-workspace entry points**: `readHandoffState` (`tools/handoff-parse.ts`), before it calls the shared `readAndMigrate`, and `writeHandoffStateCore`'s locked section (`tools/handoff-write.ts`), before `handoffPath` is resolved for the write. It is **deliberately NOT** placed inside `readAndMigrate` or `parseHandoff` themselves — those two are the SHARED read primitive that cross-workspace callers (`tools/feature-rollup.ts`, `tools/join-precondition.ts`, `tools/storage.ts`, `tools/tasks-file.ts`) also call, directly or transitively, for workspaces that are not "their own" (see AC13 — a migration trigger living there would move files in a workspace the caller never asked to mutate). Trigger condition (both own-workspace sites, same predicate): a flat `<ws>/.current/handoff.md` exists on disk AND `resolveCurrentLanePaths(ws).handoffPath` (the lane-scoped path) does not yet exist. A workspace with no flat handoff (a fresh worktree, or one already migrated) never enters the migration branch. See AC14 for the third case (both paths exist).
  proof: a fixture workspace with only a flat handoff — the first `tw_get_state` call (own workspace) returns lane-scoped state and the lane directory now exists on disk; a second call is a no-op read (AC4 covers this explicitly). A second fixture, read via `parseHandoff` directly (simulating a cross-workspace caller) instead of `readHandoffState`, returns the flat state correctly but performs no move (AC13's proof covers this explicitly).

- **AC4 (trigger-once)** — After AC3's migration runs, the flat `.current/handoff.md` (and every other moved `LANE_FILES` entry) no longer exists at the workspace root, so AC3's trigger predicate is false on every subsequent call for that workspace — no flag file, no second migration, no loop. If `migrateFlatToLane` throws (required entry missing mid-race, destination conflict), the read/write surfaces that error rather than silently proceeding against stale flat paths or retrying in a loop.
  proof: call `tw_get_state` three times in a row against the same fixture; only the first call's before/after disk snapshot shows a move; calls 2 and 3 are byte-identical no-ops.

- **AC5 (Decision 2 — lock path — decided 2026-09-23: per-lane)** — The handoff lock moves from workspace-wide (`.current/.handoff.lock`, J1) to per-lane: `writeHandoffState`'s `lockPath` (`tools/handoff-write.ts`) and `migrateFlatToLane`/`migrateLaneToFlat`'s lock (`tools/lane-migrate.ts`) both resolve to `.current/<lane>/.handoff.lock`, where `<lane>` is `resolveCurrentLane(workspacePath)` for a live writer and the migration's own destination lane (AC2) for the migration runners. Because the lane directory may not exist yet at lock-acquisition time, the lock acquirer creates it first (`fs.mkdirSync(..., { recursive: true })`) purely to host the lock file — this is the same `ensureDir`-before-lock ordering J1 already established for the handoff file itself, applied to the lock's own directory. This makes the migration and a live per-lane writer serialize against the SAME lock for the SAME lane during the migration window (AC-MIG-3), which workspace-wide locking would no longer guarantee once writers move to per-lane locks. **See AC12**: because `writeHandoffStateCore` now needs to run the migration (AC3) from inside its own locked section, and the migration runner also wants that same lock, the lock is no longer safely re-entrant by simple nesting — AC12 is the fix.
  proof: `HANDOFF_LOCK_FILENAME`'s literal stays the single owned constant (J1 AC3, unchanged); a new table test asserts the resolved lock path for a lane workspace is `.current/<lane>/.handoff.lock`, not `.current/.handoff.lock`.

- **AC12 (non-reentrant lock)** — `withFileLock` (`guards/file-lock.ts`) is `O_EXCL`-based and cannot be re-entered on the same call stack: it would deadlock (or, more precisely, wait its own `LOCK_MAX_WAIT_MS` and then fail) if a caller already holding a lock tries to take it again. `writeHandoffStateCore` (`tools/handoff-write.ts`) acquires the per-lane lock (AC5) and, inside that locked section, must trigger the migration (AC3) when it detects a flat-only workspace — but `migrateFlatToLane`'s exported form also acquires that same lock itself. `tools/lane-migrate.ts` splits each runner into a lock-free core (`migrateFlatToLaneLocked(workspacePath, opts)` / `migrateLaneToFlatLocked(workspacePath, lane, opts)`) plus a thin public wrapper that acquires the lock and calls the core — the exact shape `writeHandoffStateCore` itself already uses for `writeHandoffState`/`writeHandoffStateCore`. `writeHandoffStateCore` calls the **locked core function directly** (it already holds the lock); every other caller (including `readHandoffState`, which does not pre-hold any lock) calls the **public, lock-acquiring wrapper**. Nothing anywhere acquires the same lock path twice on one call stack.
  proof: a test that calls `writeHandoffState`/`tw_update_state` against an unmigrated flat fixture completes within a bounded timeout (e.g. well under `LOCK_MAX_WAIT_MS`), does not hang, and the resulting state is migrated — the regression this AC exists to prevent is exactly a silent hang/timeout on this path.

- **AC-MIG-3 (concurrency-safety)** — Two concurrent calls against the same unmigrated flat workspace (any mix of `tw_get_state` / `tw_update_state`) never (a) both perform the move, (b) observe a half-moved file set (some `LANE_FILES` entries at the old path, some at the new one), or (c) lose a write issued during the migration window. This falls out of AC5's per-lane lock being acquired for the whole migration critical section (pre-flight checks through the renames) — via AC12's locked-core split, so the lock is held exactly once per call stack — exactly as `withFileLock` already serializes `migrateFlatToLane`'s own moves today (`tools/lane-migrate.ts`'s existing header comment). AC5 only changes which lock path is held; AC12 keeps it held exactly once; neither changes the underlying serialization guarantee.
  proof: fire two simultaneous `tw_get_state` calls (or one `tw_get_state` + one `tw_update_state`) against a fixture flat workspace; assert exactly one migration occurred (single before/after disk diff), the resulting lane `handoff.md` parses as well-formed YAML, and neither caller errors or times out.

- **AC6 (Decision 3 — `.current/archive/` scope — decided 2026-09-23: stays workspace-wide)** — `writeHandoffState`'s per-write feature-change archive (`archiveDir = path.join(workspacePath, ".current", "archive")`, `tools/handoff-write.ts`) is **unchanged** — it already resolves at the workspace root, not per-lane, so Decision 3 requires no code change, only a comment recording that this was a decided question (J1-NEW-1), not an oversight: filenames are globally unique (`<sanitized-feature>.<pid>.<epoch>.md`) and E157 already gitignores the directory, so there is nothing a per-lane split would buy and a real cost (an archive entry outliving the lane dir that produced it, on lane close/reuse) it would introduce.
  proof: `git diff` on `tools/handoff-write.ts` for this AC shows only a comment changed, no logic.

- **AC13 (own-workspace-only migration; cross-workspace reads stay read-only)** — The migration (AC3) fires **only** on the `tw_*` read/write path for the server's own `workspace_path` argument — never as a side effect of reading some OTHER workspace's state. `tools/lane-registry.ts` (`getLaneFeatureHistory`, `laneRegistryList`), `tools/feature-rollup.ts` (`localFallbackLaneList`, `computeFeatureRollup`), `tools/join-precondition.ts`, and any future cross-workspace reader all reach handoff content exclusively through `parseHandoff`/`readAndMigrate` (`tools/handoff-parse.ts`) — **never** through `readHandoffState` — so routing the trigger out of the shared primitive (AC3) already keeps these callers non-mutating by construction; this AC's job is to make sure they still see correct data for an unmigrated workspace instead of a false "no handoff found". `readAndMigrate` resolves the handoff path with a **read-only fallback**: try `resolveCurrentLanePaths(ws).handoffPath` (the lane path) first; if it does not exist, fall back to reading the flat `<ws>/.current/handoff.md` if THAT exists; if neither exists, behave as today (`null`/not-found). No lock is taken, nothing is moved or created, in either branch. This one fallback lives in the single shared function every reader (own- and cross-workspace) already goes through, so `tools/feature-rollup.ts`/`tools/join-precondition.ts` need no code changes of their own to see an unmigrated lane's real state (a live not-yet-touched worktree currently would have read as `readable: false` post-AC1 without this fallback — a real regression this AC exists to prevent).
  proof: a cross-workspace read (`parseHandoff(otherWs)`, simulating `tools/feature-rollup.ts`'s call pattern) against a flat-only fixture returns the flat state correctly; a per-file SHA-256 comparison of that fixture's `.current/` tree before and after the read is byte-identical (nothing moved), and no lane directory or lock file was created.

- **AC14 (dual-presence conflict — scoped to `handoff.md` ONLY)** — If BOTH the flat `<ws>/.current/handoff.md` and the lane-scoped `<ws>/.current/<lane>/handoff.md` exist simultaneously (the exact state a pre-flip MCP server produces if it writes the flat file again after this workspace has already been migrated — see the Rollout note below), `readAndMigrate` throws a distinctly-named error, `HANDOFF_LAYOUT_CONFLICT` (a plain `Error` with that string as a recognizable prefix/code in its message — **deliberately not** a `GateErrorCode`/`GATE_REGISTRY` entry, confirmed with the human: it fires on reads too, outside the mutating-tool gate pipeline `test/error-code-contract.test.mjs` governs, and its name carries no `_REQUIRED`/`_MISSING`/`_EXCEEDED`/`_UNVERIFIED`/`_REJECTED`/`_UNRESOLVED`/`_MISMATCH`/`_HELD`/`_CHANGE`/`_SUSPECT` suffix or `MISSING_` prefix, so it does not enter that test's shape-rule vocabulary and needs no `content/*.md` doc mention — confirmed against `test/error-code-contract.test.mjs`'s `SUFFIX_RE`/`PREFIX_RE`). **This AC applies ONLY to `handoff.md`** — the required `LANE_FILES` entry. A sidecar (`telemetry`/`metrics`/`usage`/`dispatch.jsonl`) present at both the flat and lane path is never a conflict; it is AC15's merge case. It is never silently resolved by picking one side, and the migration trigger (AC3) never overwrites either file when it detects this state — the throw happens before any move is attempted. Surfacing paths: **own-workspace read** (`tw_get_state` → `readHandoffState` → `readAndMigrate`) and **own-workspace write** (`tw_update_state` → `writeHandoffStateCore`) both let this error propagate to the tool caller as a hard failure (an operator must resolve the conflict by hand before the workspace is usable again; this ticket does not build an auto-resolver, matching §3.2's "no second judge" posture E126 already declined for merge conflicts). **Cross-workspace readers** (AC13's list) already wrap `parseHandoff` in `try/catch` and degrade to `readable: false` with the caught error's message (the existing best-effort posture `tools/feature-rollup.ts` already has for any unreadable handoff) — they must NOT throw further into the registry; this AC requires only that the caught message clearly names the conflict (via the `HANDOFF_LAYOUT_CONFLICT` prefix) rather than reading as a generic parse failure, so a human scanning `lane_registry` output can tell "dual presence" apart from "malformed YAML" or "no handoff found".
  **Message content, mandatory (three elements)**: the thrown error's message must include (a) **both absolute file paths** (the flat `<ws>/.current/handoff.md` and the lane `<ws>/.current/<lane>/handoff.md`, fully resolved, not relative); (b) **each file's `last_updated` value** — parsed from that file's own frontmatter, or the literal string `"unparseable/missing"` if it has none or the value doesn't parse — so an operator can tell which side is newer without opening both files by hand; (c) **concrete repair steps**, in order: stop/restart every running MCP server for this workspace (AC14's Rollout note is the reason why), decide which file is the one to keep (typically the newer `last_updated`, but the operator's call — the server does not decide this for them), delete or move the other file out of `.current/`, then retry the `tw_*` call.
  **Rollout note**: after this ticket merges, **every running MCP server instance (every IDE/session, primary checkout and every worktree lane) must be restarted.** An old, pre-flip server process keeps resolving `resolveCurrentLanePaths` to the flat path and will keep writing `.current/handoff.md` directly — even after some other, restarted server has already migrated that same workspace to `.current/<lane>/handoff.md` — producing exactly the dual-presence state this AC detects. This is a hard operational requirement, not a nice-to-have; record it in the release notes for whichever ticket ships this flip.
  proof: (a) a fixture with both a flat and a lane handoff present, each with a distinct (and one with a missing) `last_updated` — `readHandoffState`/`tw_get_state` and `writeHandoffState`/`tw_update_state` both reject with an error whose message contains `HANDOFF_LAYOUT_CONFLICT`, both absolute paths, both `last_updated` values (or `"unparseable/missing"`), and the three repair steps, and neither file is modified or deleted; (b) the same fixture read via `parseHandoff` directly (simulating a cross-workspace caller) does not throw past the existing `tools/feature-rollup.ts` try/catch — the resulting `LaneInfo` has `readable: false` and an `error` string containing `HANDOFF_LAYOUT_CONFLICT`; (c) a fixture with a flat AND lane `usage.jsonl` (no handoff.md conflict) does NOT throw — see AC15.

- **AC15 (sidecar merge at migration)** — The four **optional** `LANE_FILES` entries (`telemetry.jsonl`, `metrics.jsonl`, `usage.jsonl`, `dispatch.jsonl` — append-only logs, never the required `handoff.md`) can legitimately exist at the lane destination BEFORE `migrateFlatToLane` ever runs: e.g. the usage hook (`bin/agent-governance-usage-hook.mjs`) resolves its path via `resolveCurrentLanePaths` directly (AC1) and appends to `.current/_primary/usage.jsonl` on the very first `PostToolUse` event, independent of and possibly before the first `tw_*` call that would trigger the handoff migration (AC3). This is normal, expected, and MUST NOT reject or throw. In `tools/lane-migrate.ts`'s `*Locked` core (AC12's split — owned by T-E123B9-01, the same file as AC2/AC5/AC12): when a sidecar's flat source and lane destination BOTH exist, the two are **merged**, never refused — the flat file's lines come first (oldest — the file that predates the lane directory), then the lane file's own pre-existing lines (newest — activity that already happened in the lane), concatenated and written **atomically** (tmp file + `fs.renameSync`, the same publish primitive every other writer in this codebase uses) to the lane path, under the **same per-lane lock** the rest of the migration critical section already holds (AC-MIG-3) — no new lock, no separate critical section. The flat source file is then removed, exactly as for any other successfully-moved entry. The required `handoff.md` entry is UNCHANGED by this AC — its destination-exists case is still refuse-on-different-content (AC14 handles that one layer up, before `migrateFlatToLane` is even called) or the pre-existing idempotent-resume case (byte-identical dest, drop the source).
  **The reverse runner (`migrateLaneToFlat`) is UNCHANGED for sidecars** — its existing "destination exists with different content → refuse, touch nothing" posture stays exactly as it is today. Unmerging a sidecar that was merged on the way in is not well-defined (which lines came from which side is no longer recoverable once concatenated), so the reverse direction deliberately does not attempt it; a flat-side conflict on the return leg is treated the same as any other unexpected foreign state — refuse loud, change nothing.
  **AC8 stays byte-reversible**: AC8's reversibility fixtures (both rounds) copy the primary repo's real `.current/` into a **fresh** scratch workspace where **no `.current/<lane>/` directory exists yet** — so `migrateFlatToLane`'s sidecar destinations are never pre-populated, this AC's merge branch is never exercised in that test, and the round trip stays a pure move-and-move-back on both legs, exactly as AC8 already specifies. AC15 has its own, separate proof.
  proof: a fixture where the flat workspace has `telemetry.jsonl` with lines `[A, B]` and the (pre-existing) lane directory already has `telemetry.jsonl` with lines `[C, D]` — after `migrateFlatToLane`, the lane `telemetry.jsonl` contains exactly `[A, B, C, D]` in that order, the flat file is gone, and the call did not throw; the same fixture repeated for each of the other three optional entries; a control fixture with only a flat sidecar (no pre-existing lane file) behaves exactly as before (plain move, AC8 unaffected).

- **AC7 — E132 `getLaneFeatureHistory` re-point** — `getLaneFeatureHistory(workspacePath)` (`tools/lane-registry.ts`) stops scanning only `.current/archive/*.md` (a flat-layout-era proxy) and instead derives history from the lane layout directly: (a) every **live** lane — a subdirectory of `.current/` whose `handoff.md` exists, excluding the known non-lane entries `archive`, `history`, and any workspace-wide file (`.config.json`, `exemptions.json`, `feature-split.md`, `.handoff.lock`, `.agc-hook-marker.json`, role-SOP override files) — contributes its `handoff.md`'s `active_feature`; and (b) every **closed** lane under `.current/history/<YYYY-MM>/<lane>/handoff.md` (D2/D3's lane-close move target, any `<YYYY-MM>`) contributes the same way. A malformed or unreadable individual lane/history entry is skipped silently (existing posture), never aborts the scan.
  **Redefined `null`/`[]`/non-empty contract** (replaces the old archive-dir-existence rule, since there is no longer one single directory whose presence answers the question): `null` = **neither** any live lane subdirectory with a readable `handoff.md` **nor** a `.current/history/` directory exists at all — "this workspace has no lane history to report", the closest analogue to the old "archive dir doesn't exist" case. `[]` = at least one of those two sources is present (a live lane dir, or a `.current/history/` directory) but zero entries were actually parseable from it/them — "there's a place for history, but nothing readable came out of it", the old "present-but-unreadable" case. A non-empty array otherwise. **Ordering for mixed live + history entries (content-based, NOT filesystem mtime)**: every contributing entry, live and closed alike, is placed in ONE combined list ordered oldest-to-newest by each source handoff's own `last_updated` frontmatter field — **not** filesystem mtime, which a `git checkout`/`git worktree add` gives every file identically and so cannot order anything. Tie/missing rule, applied deterministically: an entry whose `last_updated` is absent or fails to parse as a timestamp sorts **last** (after every entry with a valid timestamp, regardless of how old or new those are); among entries that tie on `last_updated` (including two-or-more missing/unparseable entries), the secondary sort key is the lane name (the directory segment under `.current/` or `.current/history/<YYYY-MM>/`), ascending, for a fully deterministic order.
  proof: fixture with one live lane + two closed lanes across two different `YYYY-MM` history buckets, each with a distinct `last_updated` — `featureHistory` lists all three `active_feature` values in one list ordered by `last_updated`, oldest first, regardless of live/closed origin or file mtime (the fixture deliberately sets identical mtimes on all three files to prove mtime is not the sort key); a fourth entry with a missing `last_updated` sorts last; two entries with the same `last_updated` sort by lane name; a fixture with zero lane dirs and no `.current/history/` directory returns `null`; a fixture with a `.current/history/` directory that exists but contains no parseable `handoff.md` returns `[]`; a fixture with only the old flat `.current/archive/*.md` (no lane dirs, no `.current/history/`) now returns `null` (the flat-era signal is gone by design — this function no longer reads that directory at all).

- **AC8 (reversibility on the real flat layout, extended to exercise the wired trigger)** — Two rounds against REAL copies of this repo's own flat `.current/` (not synthetic fixtures), both entirely inside the harness scratchpad (never the repo root, §2.5):

# e296-manifest-tier-cut-approval

Lane e296 of the post-v4 wave 3 fan-out (`specs/fanout-post-v4-w3.md`, the content lane). Tickets: E296 items (1)–(8) (the cut-approval **manifest tier**); E309's one Stage 6-4 sentence in `content/skill-integrator.md` (merged into the task that already edits that file, per the manifest's cutting rule). Scope is the lane row in the manifest; it is not widened or narrowed here. Base `c392cc3`.

## Problem Statement

A fan-out costs the human one manifest approval in the integrator session plus N cut approvals typed in N lane sessions, although the object the human actually judged — the lane's owned set, scope line and ticket id — is the manifest row, and E260's Decisions show that every ruling the human made at lane level arrived through mailbox `escalate`, never at cut-approval time, except one flagged option choice (E272). The existing Constitution §3.1 Cut-Approval Auto-Tier (`cutApprovalAutoTier`, default `maxFiles` 2) never fires for lane work (E260's comment-only lanes each touched 10–20 files). The fan-out tooling cannot help: `node scripts/fanout.mjs check` diffs a committed branch, which is too late for a cut, and the Lanes table has no column where the human can mark a lane whose cut they still want to see. Separately (E309), `skill-integrator.md` Stage 6-4's BEHIND remedy still names a local full suite before the push, contradicting the CI-first rule E298 established for every other layer.

## User Stories

- As the human approving a wave, I want to approve the manifest once and have each lane's cut auto-approve when it stays inside the row I approved, so that a wave of N lanes costs me one approval plus only the rulings that genuinely need me.
- As a lane PM, I want a mechanical `check --cut` over my cut's declared file list, so that containment in the manifest row is proven by a command, not read by eye, before any approval write.
- As the integrator, I want an optional `approval` column on the Lanes table, so that at Stage 2 the human can mark the lanes (e.g. architect-hop lanes) whose cuts they still want to see, and every existing manifest keeps validating unchanged.
- As the coordinator (the sanctioned `cut_approved` writer under Task dispatch), I want the manifest tier's eight conditions and its audit line written in the constitution and my SOP, so that the auto-approval leaves the same attested trail the existing auto-tier does.
- As the integrator in Stage 6, I want the BEHIND remedy to verify by CI on the pushed branch, so that the one remaining local-suite sentence stops contradicting 5a / 5b-6 / 6-2.

## Design intent fixed by this spec (architect refines, does not reverse)

- **`## Cut` section = the inline cut table, verbatim.** One source for the chat presentation, the mailbox pre-review and `check --cut`; no second file list. Section name exactly `Cut` (existing specs use `## Cut Decisions` / `## Cut amendments` for prose — those are not read).
- **Tokenization reuses the `擁有` rules** (`pathTokens`, `isGlobToken`, `matchesGlob`, `isImplicitBookkeeping`) so a PM writes `touches` the way the integrator writes `擁有`; no new path grammar. A glob in `touches` must be the manifest's own token, otherwise the PM names the files — containment of one glob in another is never guessed.
- **`check --cut` is pure file I/O** (manifest + spec), no git, so it runs before anything is committed and is testable offline. Exit 0 means the three manifest-side conditions ((2) human row + lane row, (3) containment, (7) `approval` not `human`) all hold; the writer still checks (1), (4), (5), (6), (8) itself.
- **`approval` column is optional and ignored by `render`**: existing manifests, goldens and `render` bytes do not move. Making it mandatory or rewriting old manifests is a ticket change (manifest 所有權重劃) and is out of scope.
- **The audit line's `<date>`** is the `日期` of the latest `人類` Decisions row — the row that approved the manifest the lane is being checked against; `check --cut` prints it so the writer copies, never types.

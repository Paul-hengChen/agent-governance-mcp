# 既有測試改動清單被逐條擴充 — 2026-10-19

觀察報告，暫存於此，收斂後再轉成 `docs/backlog.md` 正式票。
狀態：`raised`（已記錄、未開票）。
來源：一個 adopter repo（Kotlin gateway＋React web console）的一次兩條 lane 的 fan-out，由整合者 session 觀察。adopter 的票號、路徑、產品名一律以類別描述。

## 摘要

一張擴充資料形狀的 web 票，切票時把「既有測試可以改哪裡」寫成**逐條列舉**的 AC（檔案:行號＋「例如」）。實作過程中又陸續冒出兩批清單外、但根因相同的紅燈，**每一批都需要一次人類裁定**才能繼續。第二次裁定時人類改採**類別式條文**，問題才收斂。

- 人類為同一件事裁定了 2 次（03:58Z、04:30Z），信箱多來回 3 次。
- 兩批新增的紅燈，根因都是同一句話：**某個型別多了一個欄位，所有對該型別做整份相等比對的既有斷言都會變紅。**
- C15 的 expected-red manifest 照設計運作：sr 準確記下了每個紅燈與根因。缺口在於 AC 的允許清單和 manifest 是兩份互不相連的清單。

lane 的交接次數在這段期間從 2 用到 5（上限 14），其中有一部分花在這兩次裁定的往返。

## 根因

1. **列舉會少算，而且少算的數量取決於測試庫。** 「型別多一個欄位」造成的紅燈數，取決於有多少既有斷言整份比對該型別，**包括間接比對**，例如共用 fixture 常數在別的檔案被 `toEqual`。PM 和 architect 靠讀碼與直覺列舉，只會抓到顯眼的呼叫點。這次漏掉的 7 個案例，全部經由一個共用 fixture 間接比對。
2. **AC 寫成「類別＋例子」，執行時卻被當成字面清單。** PM 原文其實是類別（「來源形狀多了 `fit`」），但「還原後的 profile 多了 `fits`」不在任何一個類別的字面範圍內。後續角色沒有權限自行推廣類別，只好每遇到一處就回報一次。
3. **決策權歸屬不清。** architect 認為擴充允許清單由整合者決定即可；整合者 SOP 則把「放寬完成定義」列在人類欄。「在人類**已裁定的行為**下，補上它必然造成的既有斷言改動」到底算不算放寬完成定義，SOP 沒寫。整合者為求保險一律升級給人類，結果同一件事問了人類兩次。
4. **AC 允許清單和 C15 manifest 沒有連在一起。** `qa_reports/expected-red_<feature>.txt` 已經機械地列出「哪些測試會紅、為什麼」，而且 qa Phase 0.5 會拿它和實際紅燈逐一比對。AC 的允許清單卻是另一份手寫列舉，不引用 manifest，也沒有任何核對。

## 建議（未開票）

**P1 — PM：擴充資料形狀的票，一開始就把既有測試 AC 寫成類別式。**
觸發條件：cut 會在一個既有型別上新增欄位，而測試庫中有對該型別做整份相等比對的斷言。模板如下（這次人類核准的條文，去掉 adopter 細節）：

> 既有斷言的期望值，若是整份比對（`toEqual`／`toStrictEqual` 或等價寫法）〈型別或值的類別〉，只准在期望值中補上〈新欄位〉，值必須照〈已裁定規則〉計算；matcher、其他欄位、其他值一律不准改，也不准刪除斷言。qa 報告逐條列出「檔案:行號＋補了什麼」。不屬於這一類的既有斷言改動，仍須個別裁定。

非整份比對類的必然改動（例如這次的控制項數量）仍逐條列舉。

**P2 — architect：藍圖的 Expected-red 段用 grep 推導，不靠閱讀。**
對每個被擴充的型別，grep 它的型別名與它在測試中的 fixture 常數，再找出這些常數被整份比對的位置。間接引用的 fixture 要追到使用端。產出的清單直接作為 sr 的 C15 manifest 初稿。

**P3 — `skill-integrator` Decision rights：補一條界線。**
提案：一個**類別**的允許條文第一次出現時，屬於人類欄（放寬完成定義）；人類核准類別後，落在該類別內的新增實例由整合者核對即可，不必再升級。新的類別仍屬人類欄。這樣既保留人類對「放寬」的控制，也不會為同一個類別反覆打擾人類。
（architect SOP 若有「整合者可決」的寫法，要跟這條對齊。）

**P4 — qa：類別式條文可以機械核對（選做）。**
用 `git diff <base>..HEAD` 檢查既有測試檔：被改的每一行，與原行的差異只能是「期望值物件多了被允許的鍵」。可以考慮做成輔助腳本，或併入 Phase 0.5 的 manifest 比對。

## 範圍外

- C15 manifest 本身：這次照設計運作，sr 準確記下了 blueprint gap，不需要改。
- 「既有測試只准新增」這條預設：這次的問題是例外怎麼描述，不是預設本身。

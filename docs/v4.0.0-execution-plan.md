## 0. TL;DR — 給接手 session 的五行

> ## ⛔ 最重要的一條：**波次不能同時跑**
>
> 如果你被指派「做 Wave N」，先確認 **Wave N-1 已經 merge 進 `main`**。沒有就停下來回報。
>
> 三個具體理由：**(1)** 多個波次各有自己的 `content/` lane（Wave 1 的 E91+E103、Wave 2 的 E109、
> Wave 3 的 E113…），同時跑會違反 §2.1 並**靜默汙染 golden fixture**；
> **(2)** Wave 3 的 E112–E116 全部依賴 Wave 2 的 E109 框架決定，先做等於對著未決的框架切票；
> **(3)** Wave 4 之後每一波都依賴前一波的產物。
>
> **要並行，只能在同一個波次內按 lane 分**（Wave 1 有 8 條，Wave 3 有 6 條）。

1. **先讀 §2 硬約束**，尤其是 `content/` 只能有一條 lane 這條。違反它會產生靜默的 golden 汙染。
2. 到 §4 波次表找你被指派的 **Lane 代號**，那一格列出你擁有的檔案與票。
3. **不要碰你 lane 以外的檔案。** 跨 lane 的改動一律回報，不要順手修。
3a. **分清楚「你的完成定義」和「波次的完成定義」。** 派工卡裡的核取清單有些是整個波次的
   （例如「八批全部 PASS」「合進一條整合 branch」）—— 那些屬於**整合者**，不是你。
   **你只負責自己 lane 的票走到 qa PASS，然後回報。** 不要以為整波都是你的責任，也不要去做別人的 lane。
4. 每個波次結束後才進下一個波次；波次內部的 lane 彼此無依賴，可以同時跑。
5. Tier D（§7）的票**刻意不做**，看到不要撿。
6. 過程中發現的任何缺陷或票面錯誤，**一律記進你 worktree 的 `NEW-TICKETS.md` 並在回報時點名** ——
   它們會被收進 `docs/v4.0.0-new-tickets.md`，**全部排在 v4.0.0 發版之後**，不要試圖在你這一波修掉。

## 1. v4.0.0 是什麼

**一句話**：把 lane worktree 從「feature lease 衝突時的逃生口」變成「每張票開始的地方」，
並讓治理狀態的儲存結構承受得住這件事。

### 1.0 術語（全文一致，多 session 請以此為準）

| 詞 | 意思 |
|---|---|
| **lane** | 一條**工作流** —— 一張票、一條鏈、一份自己的治理狀態 |
| **worktree** | lane 住的**地方** —— `git worktree add` 建立的獨立檢出 |

一條 lane 跑在一個 worktree 裡。「開 lane」是簡寫，實際動作是「開 worktree 並在裡面起一條 lane」。
`.current/<lane>/` 的 `<lane>` 是**工作流的名字**（票號），不是路徑名。

### 1.1 今天的狀態

`content/coord-03-core-fallback.md` 在三個地方提供 worktree 路線：Feature-Scope Gate 段落、
E111 的 *Worktree bootstrap obligation*、feature-lease 的 Escalation Routes row。
**三處都綁在「feature lease 被佔用」的條件上** —— 也就是綁在「你想要真正的並行」。
一次一張票的正常開發，照舊在 primary 做。

### 1.2 v4 之後

- 一張票 = 一條 lane worktree，由 `agc feature start` 建立（E73）
- `.current/<lane>/` 各自持有 `handoff.md`、`telemetry.jsonl`、`metrics.jsonl`、`usage.jsonl`，**維持 tracked**
- 新票不在 lane 內配號，由 release 時序列化 apply 才配（E124）
- lane 的 ledger 工作在 PR merge 後回寫進共用副本，外層 `tasks.md` / `docs/backlog.md`
  正式改成**歷史索引**而非活帳本（E125）
- 合併後有機械性的不變量檢查守著（E126）

### 1.3 為什麼是 major

三件事同時破壞既有相容性：

1. **`.current/` 的磁碟結構改變** —— schema bump + migration，舊的扁平 layout 要能被遷移
2. **`tw_*` 工具的讀取目標改變** —— 工具只看 lane 內那份，外層變成索引
3. **coordinator SOP 的預設行為改變** —— 票從 lane 開始，不是從 primary 開始

**不可逆點在 Wave 4，不在 Wave 7。** 前兩項都落在 Wave 4（E123 的分層 layout + schema bump），
第三項才是 Wave 7 的開關。所以一旦 **Wave 4 merge 進 main，舊的扁平 layout 就只能靠 migration 讀回來** ——
Wave 5 到 7 是把它變得好用、以及把開關打開，不是決定要不要走這條路。
**在 Wave 4 工作的 session 要知道自己正在越過這條線**：那一波的 migration 必須可逆驗證通過才算完成，
這是 §9 完成定義裡唯一一條講「可逆」的。

### 1.4 兩個必須在動工前解掉的設計衝突

**衝突 A：E106 與 E123 互斥。**
E106 已定的決策是 `agc init --artifacts` **預設 `local`**，寫 `.git/info/exclude`。
E123（分層版）的價值卻正是 **`.current/<lane>/` 維持 tracked，讓 lane 治理史留在 git**。
對 agc 自己沒問題（本 repo 選 `repo` 模式），但**對選 `local` 的 adopter，分層版的歷史保留完全蒸發** ——
他們只拿到目錄分層，沒有歷史。**必須在 E123 開 cut 前決定**（見 §8 待決 A）。

**衝突 B：執行 v4 的過程會踩到 v4 要修的洞。**
多個 session 平行執行 v4，需要的正是 v4 還沒建好的東西：lane 隔離、`.current/` 不衝突、
票號不撞。所以**執行期間必須用 §2 的手動紀律代替**，這不是可選項。

## 2. 硬約束（違反會產生靜默損壞，不是編譯錯誤）

### 2.1 `content/` 只能有一條 lane 【最重要】

`scripts/capture-constitution-golden.mjs` **一次重生全部 12 個 golden fixture**：

```
build-full-design.txt        build-full-design-fd.txt
build-full-nondesign.txt     build-full-nondesign-fd.txt
build-lite-design.txt        build-lite-design-fd.txt
build-lite-nondesign.txt     build-lite-nondesign-fd.txt
constitution-monolith.txt    skill-coordinator-monolith.txt
hook-full.txt                hook-lite.txt
```

`content/const-*.md`、`content/coord-*.md`、`content/skill-*.md` 任何一處改動都會動到至少一個。
兩條 lane 同時改 `content/`：

- 兩邊都重生整個 golden 目錄 → **必然衝突**
- 更糟：一次隨手的合併解法會把某一邊的內容**靜默烘焙進基準**，然後測試通過 ——
  因為 golden 只是「當下輸出的快照」，它不知道自己漏了什麼

**規則：同一時間只有一條 lane 可以修改 `content/` 底下任何檔案。**
其他 lane 若發現 `content/` 需要改動，**回報，不要動手**。

### 2.2 `test/context-budget.test.mjs` 是單一檔案、6 個 floor

同上：兩條 lane 各自調整 cap 必衝突。這個檔案跟著 §2.1 的 content lane 走。

**另注**：只調你這次真的推高的那個 floor。其他 floor 量的是**憲法本身**，
`coord-*.md` 從來不屬於 `CONSTITUTION` —— 整排一起調就是靜默退化。

### 2.3 `.current/handoff.md` 與 `tasks.md` 目前仍 tracked

> **✅ 2026-09-24 起失效（E123 J2 合併、primary 已搬進 `.current/_primary/`）**：分層之後，每條 lane 的狀態都在自己的 `.current/<lane>/`，路徑互不相同，不會再撞。**新規則（A′）**：
> - **commit 你自己的 `.current/<lane>/` 整個目錄**，連同它的 branch 一起。lane 治理史就是靠這個留在 git 裡。
> - **不要 commit `.current/` 頂層的工作檔**。`.config.json`、`exemptions.json`、`feature-split.md` 照原本的慣例處理，`archive/` 已經 gitignore（E157）。
> - 新 worktree 第一次讀取時，會把 git 裡的扁平快照搬進自己的 lane 目錄，那是陳舊狀態，不要接手。看到 `HANDOFF_LAYOUT_CONFLICT` 就停下來回報，不要自己刪檔。
> - `tasks.md` 仍然會撞，照舊逐行整合。它的處置是 E125 的事。
>
> 下面是分層之前的原文，保留作紀錄。

這正是 E123 要解的問題，但**在 E123 完成前它仍然成立**。平行 session 的手動紀律：

- 每條 lane 用**獨立的 git worktree**（`git worktree add`）
- **不要 commit `.current/*.jsonl` 與 `.current/handoff.md`** —— 它們是工作狀態，
  歷次 release 的先例是只 commit `.current/.config.json`
- `tasks.md` 會撞。整合時逐行確認，**不要**用「take ours/theirs」
- 這幾個檔案的衝突是**靜默遺失**類（見 `docs/agc-feedback-2026-09-08.md` §1(b)(c)）

> #### ⚠️ 你的新 worktree 會帶著陳舊的 handoff 出生 —— 這是預期的，不是崩潰
>
> `git worktree add` 從 **commit** 檢出，而 `.current/handoff.md` 是 tracked 的，
> 但歷次 release 都刻意不 commit 它（只 commit `.config.json`）。所以檔案裡躺的是很久以前的快照。
>
> **2026-09-16 實測**，一個新 worktree 拿到的是：
> ```
> active_feature: "e104-history-residue"
> status:         "Blocked"
> hop_count:      1        ← 來自 72f6a19，2026-09-14
> ```
>
> **你會看到一個叫 `e104-history-residue` 的 Blocked feature。不要接手它，不要跑 Crash-Resume。**
> 那不是活的狀態，是 git 裡那份快照。直接寫你自己的 `active_feature` 往下做就對了
> （lease 不會擋你 —— 那份快照的 `last_updated` 早就超過 30 分鐘 TTL）。
>
> **這正是 E123 要消滅的東西**：分層之後，新 lane 的目錄本來就不存在、由 bootstrap 當場建立，
> 沒有東西可以被繼承錯。扁平版會中毒，是因為只有一個 `handoff.md`，誰都可能是它。
> **Wave 1–3 的每個 session 都會撞到這個；Wave 4 之後不會。**

### 2.4 票號不要在 lane 內自己配

E124 要解的問題，同樣在它完成前仍成立。平行 session 的紀律：

- lane 內**不要**自己挑新票號
- 要開新票 → 寫進 lane 內的 `NEW-TICKETS.md`，**用帶 lane 前綴的代號**：`<LANE>-NEW-1`
  （例如 `L-GATE-NEW-1`、`L-STATE-NEW-1`），**不要用裸的 `NEW-1`**

> **為什麼要前綴** —— 2026-09-17 實際撞到：Session A 的 `NEW-1` 和 Session C 的 `NEW-1`
> 是**兩個完全不同的發現**（前者講合成標記寫回，後者講讀取截斷丟尾端），兩條 lane 平行回報時
> 整合者拿到兩個同名不同義的東西。裸代號在單條 lane 內沒問題，跨 lane 必撞 ——
> 這跟 E124 要解的 backlog 撞號是同一個形狀，只是發生在低一層。
- 整合時由**單一** session 序列化配號並寫進 `docs/backlog.md`

#### 配號之後排到哪裡 —— 預設是「不排進 v4」

**規則：被提升成正式票的執行中發現，一律排在 v4.0.0 發版之後，除非它擋住某個尚未完成的波次。**

判斷只有一句話：**「還沒做的波次裡，有任何一個依賴它嗎？」** 沒有 → post-v4。

**落點是 `docs/v4.0.0-new-tickets.md`** —— v4 執行期所有新發現的集中佇列，依優先順序排好。
完整票面仍然寫進 `docs/backlog.md`（那是正本）；那個檔案只排順序，一票一行。
**新票要插進正確位置，不是附加在最後** —— 排序判準、已有的票、以及誰做什麼，都在那個檔案裡。

**為什麼要有這條預設**：Wave 1 的**一條 lane** 就產出了兩張正式票。還有六個波次。
沒有預設規則，每一波都會把自己的發現塞回 v4，**v4 就會無限膨脹然後永遠發不出去** ——
這是範圍蠕變最典型的形狀，而且它**披著「這個發現很有價值」的外衣**，所以特別難擋。
發現有價值不等於它屬於 v4。它會留在 backlog 上，不會消失。

### 2.4b lane worktree 沒有 `node_modules`

`git worktree add` 不會帶 `node_modules`（它 gitignored）。**QA 跑測試前要先 `npm ci`。**
八條 lane 每一條都會撞到 —— 2026-09-17 由 Session B 回報，此前 E111 的 lane 也踩過同一件事。

**這正是 E73 的 `agc feature start` 要吸收的成本**（Wave 5），在那之前每條 lane 自己跑一次。

### 2.5 shell cwd 會重置回 primary（E127，無解法）

**已在 2026-09-15 實際造成汙染**：fixture 被建進 primary 並 commit 進 main。
harness 每次 Bash 呼叫後 cwd 都重置回 primary，多次呼叫搭 fixture 時每次都從 primary 重新開始。
33 個 gate 沒有一個看得到 `workspace_path` 以外的檔案系統寫入。

**紀律**：每個會建立檔案的 bash 呼叫都要在同一次呼叫內 `cd`，或使用絕對路徑。
fixture 一律建在 `$TMPDIR` 或 scratchpad，**永遠不要**在 repo 根目錄建臨時目錄。

### 2.6 feature lease 是 per-workspace

不同 worktree = 不同 `workspace_path` = 各自的 lease，天然隔離、零伺服器成本。
**所有 `tw_*` 工具都要傳自己 lane 的路徑**，不要傳 primary。

### 2.7 §2 憲法：只有 qa-engineer 能碰 `test/`

跨所有 lane、無例外。sr-engineer 看到紅燈要回報不要修。

## 3. Lane 檔案所有權

並行的基礎是**檔案互斥**。下表是每條 lane 獨佔的檔案；不在你格子裡的檔案不要碰。

| **L-INIT** | `bin/agc-init.mjs`、`bin/agent-governance-*.mjs`、`templates/` | CLI 與樣板 |
| **L-RENDER** | `prompts/build.ts`、`prompts/*-manifest.ts`、`lib/` | 組裝路徑 |

> #### ⚠️ 一張票的檔案跨越多條 lane 時 —— 拆票，不要硬塞
>
> **這份計劃在 Wave 1 犯了這個錯五次**（2026-09-17 由 Session B 指出三處，coordinator 稽核再找到兩處）。
> 根因不是筆誤：**§3 用檔案劃 lane、§4 把票指派給 lane，而這兩份對應表從未交叉對帳。**
>
> **規則**：指派前先問「這張票的**所有**檔案，裝得進那一條 lane 嗎？」
> 裝不進 → **按 lane 拆成兩半，並在票面明寫哪一半歸誰**，不要整張塞給其中一條然後期待它自己處理。
>
> 這個錯的後果不是編譯失敗，是**半套上線**：Wave 1 的 E84 工具落地了，
> 但「讓角色真的會去跑它」的那行 SOP 在 `content/`，L-RELTOOL 碰不得，
> 所以**工具存在而沒有任何角色被告知要跑**。B 正確地回報而不是越界。

**測試檔**：每條 lane 的 qa 只碰自己那張票的測試檔。共用測試檔（`test/context-budget.test.mjs`、
`test/render-structure.test.mjs`、golden fixtures）**一律屬於 L-CONTENT**。

## 4. 波次執行計劃

**規則**：同一波次內的 lane 彼此無依賴，可同時跑。跨波次必須等前一波全部整合完畢。

### 4.0 全波次總覽 —— 每一波做完得到什麼

|---|---|---|---|
| **0** ✅ | 六個裁決（A–F） | — | 六題全部有答案，沒有波次再卡在人類裁決上 |
| **1** ✅ | `E92+E86`・`E128`・`E82+E83+E84`・`E88+E105`・`E120+E131`・`E122`・`E91+E103`・`E102` | **8 條** | 既有缺陷清乾淨（四張在 2026-09-15 真實咬過），**外加 Wave 0 裁決 C/E 的實作** |
| **1.5** ✅ | `E83`・`E82 (ii)`・`E84 接線` | 1 條 | **content 補課（修正規劃錯誤）** —— Wave 1 落地的工具沒有任何角色被告知要跑，散文也還停在舊數字 |

### ✅ 待決 A（已決 2026-09-16）—— E106 與 E123 的關係

**結論：分層版對兩種模式都生效；`local` 模式下它是 no-op，不需要特別處理。**

推理比原本的三選一更簡單：`local` 模式下 `.current/` 本來就被 `.git/info/exclude` 排除 ——
**沒有東西被追蹤，就沒有東西會衝突**。分層版對那些使用者既不有害也不有用。
所以精確的敘述是「**分層版只在 `.current/` 被追蹤時才有意義**」，其他情況是無害的空轉。
不需要 `agc check` 去分辨兩種 layout，E106 的 `local` 預設也不必重新檢討

### ✅ 待決 B（已決 2026-09-16）—— worktree 的觸發條件

**結論：一體適用，但用條件觸發，不是無條件預設。** 三條觸發線：

### ✅ 待決 E（已決 2026-09-16）—— E102 R3-A

**支援 symlink；明確不支援 hardlink。**

問題形狀：`agc init` 用 `atomicWriteFile`（tmp + `renameSync`）寫 `CLAUDE.md`，那會**換掉 inode** ——
symlink 被刪除換成獨立實體檔，使用者真正維護的那份從未收到 adapter block，
而 `agc check` 接著對著脫鉤的副本回報 **OK**。無聲失效，發生在使用者最確信它生效的地方。

**拍板的論證是一個內部矛盾**：E111 剛在**同一個檔案**裡 ship 了一條規則，叫 adopter 用 **symlink**
把三個證據目錄連回 primary，而 `checkWorktreeEvidence` 大半篇幅都在用 `lstatSync` / `isSymbolicLink` /
`realpathSync` 驗證那些連結是否正確 —— 同一支 binary，一邊教人用 symlink，一邊把 symlink 毀掉。
「本 repo 和該 adopter 專案的 `CLAUDE.md` 都不是連結」只證明**我們**沒用這種 layout，不證明 adopter 沒用，
而 E73 的立論本來就是這一類票服務的是 adopter workspace。

**兩個實作要點**：(1) `realpathSync` 遇到 dangling symlink 會**丟例外**，要 fail-closed ——
先例就在幾百行外的 `checkWorktreeEvidence` 裡。(2) **hardlink 是決定不支援，不是疏漏** ——
hardlink 沒有「目標」可解析（它是同一個 inode 的第二個名字），`realpathSync` 幫不上忙；
唯一有效的作法是退回截斷式就地寫入，而那正是 T-E100-03 為了消除 `^C`/ENOSPC 截斷風險才換掉的。
截斷風險更常見也更嚴重，所以 hardlink 宣告不支援，並在程式碼註解裡寫明理由。

### ✅ 待決 F（已決 2026-09-16）—— 半途作廢的 lane 怎麼收

**兩包產物分開處置，因為它們性質不同：**

| 產物 | 處置 | 理由 |
|---|---|---|
| **新發現（待開的票）** | **套用進 backlog**，票號在那一刻配發（與正常路徑相同） | 你在做 E140 時發現的問題，不會因為 E140 被放棄就不存在 |
| **證據報告** | 歸到 `abandoned/` 子樹或丟棄 | 它們描述的是沒有 ship 的程式碼。重點是**明確決定**，而不是默默消失 |

**機制**：`agc feature finish` 是**唯一被認可的拆除方式**，兩條路徑 —— `--shipped`（正常回寫）與
`--abandoned`（套用發現、處置證據、在紀錄裡標明這條 lane 被放棄）。這是 E73 的 `finish` 多做一件事，
不是新機制。直接 `git worktree remove` 因此屬於**未定義行為**，文件要明說。

**偵測器是必要的，不是可選的 —— 這一點決定整條規則有沒有用。**
任何倚賴「有人記得執行收尾」的方案，都會在最需要它的那一刻失效，因為**放棄一張票正是人停止關注它的時刻**。
這是量過的，不是假設：一個 adopter 驗收專案在 2026-09-08 掉了 7 張票裡 4 張的證據，
原因從來不是搬運做錯，而是**搬運那一步沒有發生**。E111 整張票的存在理由就是消滅那個可被遺忘的步驟；
在這裡重新引入一個，等於重蹈這個 repo 剛花一次發版修掉的缺陷。

可偵測的形狀很便宜：**有 branch 帶著未套用的待開票檔、但 worktree 已經不存在** —— 那是孤兒，
而 **E132 的推導式 lane 清單已經提供了比對的另一半**。由 `agc check` 或 Backlog Intake Loop 報出來即可。

## 8b. 開 cut 前的常設檢查 —— 「這個決策指名的東西，在 adopter workspace 存在嗎？」

**這一節是 Wave 1 兩起偏離的根因分析，由執行 L-CONTENT+L-INIT 的 session 指出（2026-09-17）。
它比那兩起偏離本身重要，因為 §8 還有四個決策要餵給 Waves 2–8，而它們是同一個 session
用同樣的方式寫的。**

### 發生了什麼

兩條不同的 lane 偏離了兩個不同的 Wave 0 決策，回報時看起來像兩起無關的意外。**它們是同一個根因**：

| 決策 | 指名了什麼 | 為什麼在 adopter 那裡不成立 |
|---|---|---|
| **C**（E103） | `content/skill-<role>.md` 作為 dispatch pin 的解析來源 | **`agc init` 從不 scaffold `content/`** —— 伺服器有（`tools/role.ts:22` 從 server root 解析），但 coordinator 是 agent，它看的是工作區。照字面讀，對每一個 adopter 都解析不到東西 |
| **E**（E102） | 在 `realpathSync` 拋例外處 fail-closed | 那個分支到不了 —— 呼叫端自己的 `existsSync` 對 dangling symlink 已經回 false |

**共同形狀：決策是對著「本 repo 的 layout」驗證的，不是對著「這段程式碼實際會遇到的狀態」驗證的。**

### 最該記住的部分

**決策 C 甚至記了一個驗證步驟，而那個檢查通過了，卻剛好錯過重點。**
票面寫著「已驗證：11 個 `recommended_model` 與已安裝的 `~/.claude/agents/*.md` 完全一致」——
比對的**兩個來源都只存在於本 repo 的環境**，從來沒問「managed workspace 裡有沒有其中任何一個」。

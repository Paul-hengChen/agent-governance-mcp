## Context

The lane launcher (`scripts/lane-launch.mjs`) starts the lanes of one wave. A planned conductor role (E466) will
open a fresh integrator session for every wave instead of keeping one integrator open for a whole manifest
(discussion record `docs/discussions/2026-11-27-integrator-session-rotation.md`, rulings R5, R6, R11, R13, R15).
This ticket gives the launcher what the conductor needs: a per-repo setting for when a wave counts as done, a
dependency rule that is correct when the next wave starts before the previous pull request merges, a way to
wake lanes paused on the weekly usage limit, and a way to close the windows of lanes that have finished.

Out of scope: the conductor role itself, its state file and mailbox, and any integrator SOP change (all E466);
any server change.

## Scenarios

### S1 — Wave-done setting defaults to merged

- Given a `.current/.config.json` with no `waveDoneAt` key
- When the configuration is loaded
- Then the wave-done value is `merged`
- And a file that sets `waveDoneAt` to `pr-open` loads as `pr-open`
- And any other value is reported by name and loads as `merged`
- Verification: test test/e465-config.test.mjs — S1: any other waveDoneAt value is reported by name and resolves to merged, never a config error

### S2 — In pr-open mode a dependency waits for merged code

- Given `waveDoneAt` is `pr-open`, lane C of wave 2 depends on lane A of wave 1, and lane D of wave 2 depends on nothing
- And lane A has been through `agc feature finish --shipped`, but the pull request carrying A has not merged into the ref wave 2 starts from
- When the launcher runs for wave 2
- Then D is started
- And C is not started and is listed as waiting, with a reason naming A's work as not yet merged
- Verification: test test/e465-dependency.test.mjs — S2: pr-open, A shipped but its pull request not merged — D starts, C waits naming A's work as not merged into main

### S3 — The waiting lane starts once the work has merged

- Given the situation of S2 after the pull request carrying A has merged into the ref wave 2 starts from
- When the launcher runs again
- Then C is started from that ref and D is not started a second time
- Verification: test test/e465-dependency.test.mjs — S3: after the pull request carrying A merges into main, a re-run starts C from main and does not start D again

### S4 — Merged mode keeps today's dependency rule

- Given `waveDoneAt` is absent or `merged`
- When the launcher decides whether a dependency is met
- Then the result is the same as before this ticket for every case the existing launcher tests cover
- Verification: test test/e465-dependency.test.mjs — S4: merged mode — the E443b dependency reasons are unchanged (not an ancestor; gone without finish record; knowledge local)

### S5 — A weekly-paused lane is woken only when asked

- Given a lane recorded `paused-weekly` whose window still exists
- When the launcher runs without the weekly-wake option
- Then that lane is not woken and stays `paused-weekly`
- And when the launcher runs with the weekly-wake option, it sends the existing wake line into the same window, with no new window and no `agc feature start`, and the lane is recorded `running`
- Verification: test test/e465-window.test.mjs — S5: without --wake-weekly a paused-weekly lane is not woken; with it the wake line goes into the same window and the lane is running

### S6 — Finished lane windows are closed, stopped ones are kept

- Given a wave with lane A finished, lane B whose ticket status is `stopped — awaiting manual verification`, and lane C whose ticket status is another `stopped — …` value
- When the launcher runs with the close-finished option
- Then it sends `/exit` to A's window only, using the window id in the launch state
- And B's and C's windows stay open, and the launch state records A's window as closed
- Verification: test test/e465-window.test.mjs — S6: --close-finished sends /exit to the finished lane's window only, keeps stopped lanes' windows, records it closed

### S7 — The options are documented

- Given `docs/config.md` and `docs/lane-protocol.md`
- When they are read
- Then `docs/config.md` documents `waveDoneAt` with both values and the default, and the launcher's usage text names the weekly-wake and close-finished options
- Verification: test test/e465-config.test.mjs — S7: docs/config.md documents waveDoneAt with both values and the default, right after the laneLaunchLimit section

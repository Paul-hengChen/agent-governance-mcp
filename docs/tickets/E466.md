## Context

Today one integrator session must stay open from the first wave of a manifest to the last: only it starts the
next wave, so its context keeps growing, against the operator's rule that each wave gets a fresh session. This
ticket adds the conductor (`conductor`, the fourteenth prompt), the only long-lived session: it opens an
integrator for a wave, waits for that integrator's wave-done report, checks the facts, closes it, and opens a
fresh integrator for the next wave (discussion record `docs/discussions/2026-11-27-integrator-session-rotation.md`,
rulings R1, R2, R4, R7–R14, R16). Window actions are a script the conductor calls; judgment and notices stay with
the conductor session.

Out of scope: the launcher setting, dependency rule, weekly wake and window closing (E465, used here); moving
across manifests (a new manifest always needs the human); any server change; tmux or background sessions.

## Scenarios

### S1 — The conductor is a registered prompt-only role

- Given a registered server
- When the prompt list is requested
- Then `conductor` is in it and the list holds fourteen prompts
- And `tw_switch_role` rejects `conductor` as a role
- Verification: automated test

### S2 — The conductor SOP states its loop and limits

- Given the composed `conductor` prompt
- When it is read
- Then it says: start from an approved discussion record and open the first integrator with `fan-out <record>`; open every later integrator with `接手 <manifest>` and the wave number; after the last wave, notify the human and stop; never start another manifest
- And it contains no `tw_update_state` instruction
- Verification: automated test

### S3 — Opening and closing an integrator window

- Given a stand-in window driver
- When the conductor script is asked to open an integrator for wave 2 of a manifest
- Then it opens one window, sends the integrator prompt line followed by `接手 <manifest>` and the wave number with the send method the launcher uses, and records the window id
- And when asked to close it, it sends `/exit` to that window id only
- Verification: automated test

### S4 — State survives a lost conductor

- Given a conductor run that has recorded its manifest, current wave, integrator window id and current step
- When a fresh conductor reads the state file
- Then it reports the same manifest, wave, window id and step
- And the state file lives in the directory `git rev-parse --git-common-dir` prints and is not tracked
- Verification: automated test

### S5 — A wave-done report is checked before the integrator is closed

- Given a `type: report` wave-done message in the conductor's mailbox
- When `waveDoneAt` is `merged` and the wave's pull request has not merged, or `handoff --check` does not exit 0
- Then the integrator is not closed and the conductor replies naming the unmet fact
- And when the pull request has merged (or, under `pr-open`, is open) and `handoff --check` exits 0, the conductor closes the integrator, closes the finished lane windows with the launcher's close-finished option, and opens the next wave's integrator
- Verification: automated test

### S6 — A vanished integrator is reported, not reopened

- Given a wave in progress whose integrator window no longer exists and no wave-done report has arrived
- When the conductor checks
- Then it notifies the human that the integrator is gone and which wave it held
- And it opens no new integrator window
- Verification: automated test

### S7 — Waking after usage limits

- Given the conductor SOP
- When it is read
- Then it says: after the conductor's own automatic continue following a session-limit reset, wake the paused integrator and re-run the launcher to wake `paused-stopped` lanes; after the human says the weekly limit has reset, also wake `paused-weekly` lanes with the launcher's weekly-wake option
- Verification: automated test

### S8 — The integrator SOP works with the conductor

- Given `content/skill-integrator.md`
- When it is read
- Then it says the integrator reports wave-done to the conductor's mailbox at the moment `waveDoneAt` names
- And under `pr-open` it watches the earlier wave's pull request and re-runs the launcher when it merges, and its own wave is not done until those waiting lanes finish
- And it no longer names "after a usage limit resets" as a moment to re-run the launcher
- Verification: automated test

### S9 — A real two-wave run rotates the integrator

- Given this repository or a small project with an approved manifest of at least two waves
- When the conductor runs it end to end
- Then a person sees integrator 1 closed after wave 1, integrator 2 take over wave 2, and the finished lane windows closed
- Verification: device-or-person: watch one real two-wave run and confirm each step above

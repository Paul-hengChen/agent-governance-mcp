## Correctness

- **[recommended] AC6 integrator condition (ii) — receipt is not byte-identical to the pre-change forward for the routine marker-bearing case.** T-E125C-04's dispatch brief asked me to judge this explicitly, so: the *Definitions* section of the spec (not just AC6's own text) mandates `primaryIndexReceiptSha` be "used by the forward stamp" unconditionally, and AC3 (a numbered, non-negotiable AC) requires the reverse to tolerate root-side marker removal — which is only possible if the receipt hash ignores marker lines. I confirmed by direct construction (`primaryIndexReceiptSha(body)` vs the pre-change `sha256(body)` on a no-CL body containing one marker line) that these differ whenever the body carries a marker line or a non-canonical trailing-newline shape. Given this codebase's own design (a feat lane's forward migration commonly leaves a marker in the *same* root before `_primary`'s own v1→v2 forward ever runs — see `tools/tasks-lane-migrate.ts:391-405`), a marker-bearing no-CL root is the **normal** case, not a contrived one. I judge the implementation correct and necessary (AC3 cannot hold otherwise, and sr disclosed this transparently in `pending_notes`), but it is a literal breach of the to-lane#1 integrator's condition (ii) as worded ("byte-identical... receipt..."), for that subset of inputs. Functionally nothing regresses — AC5's raw-sha fallback means a legacy or freshly-produced receipt both validate on reverse — but the receipt *file's bytes* differ from what the pre-E125c code would have written. This needs an explicit integrator/PM ruling (accept the deviation, or narrow condition (ii)'s wording to canonical bodies) before the Wave 8 gate is signed off as fully satisfying it; I am not blocking APPROVED on it since there is no code change that satisfies both AC3 and the literal condition (ii) simultaneously.
- **[recommended] A hand-fabricated `tasks_moved` marker line is silently absorbed, not refused.** Question (1) in the dispatch brief asked whether stripping markers + CL opens a hole. It does, narrowly: `normalizeIndexBody` strips *every* line matching `MARKER_LANE_RE` regardless of whether it corresponds to a real lane extraction. I hand-added a marker line for a lane (`zzz-fake`) that was never part of any real migration, appended it to a post-forward root, and reverse *succeeded* (no refusal) and *silently dropped* the fabricated line from the restored v1 root rather than surfacing it as an unsanctioned change. AC4's contract ("a hand-edited, added or removed task row or prose line" refuses) doesn't literally cover marker lines either way, so this isn't a spec violation, but it means a hand-edit that happens to look like a marker comment bypasses the "touches nothing unless sanctioned" guarantee X4b is trying to give. Low real-world severity (garbage in, garbage silently vanishes, no data corruption), worth a follow-up hardening ticket (e.g. only tolerate a root marker's *absence* relative to the ledger, never tolerate a marker present in root but absent from ledger).
- **[optional/informational] `## Closed Lanes` content itself is never receipt-checked at all, by design.** A hand-edit purely inside the CL section (e.g. corrupting a `lane_closed:` pointer's `branch=` value) passes reverse without refusal and the corrupted text is carried verbatim into the restored root. This matches the CL section's documented role (root-index-only, tool-appended, never part of the ledger the receipt protects) — it is not a new hole introduced by this diff, since CL content was never part of the forward receipt's input even before E125c. Flagging for completeness per the dispatch brief's question (1), not as a defect.
- No other correctness issues found. Lock ordering, refusal-before-write ordering, and the `SECTION_OR_TITLE_RE`/`CLOSED_LANES_HEADING_RE` re-declaration (necessarily duplicated from `bin/agc-init.mjs`, which is out of scope per spec Out-of-Scope) are all consistent with the existing e125a/e125b design and unchanged by this diff except where documented above.

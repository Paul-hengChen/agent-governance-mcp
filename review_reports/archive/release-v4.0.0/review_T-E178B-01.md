## Correctness
- **[required] tools/lane-status.ts:1417** — `fields.push([WATCH_PREREVIEW_KEY, check.state === "sent" ? check.text : check.state])` bypasses `watchValue()`. Every other watched field goes through `watchValue(values[k])` (tools/lane-status.ts:1403), whose own docstring says values are "whitespace folded to `_` so the state line stays one line of `key=value` tokens" (tools/lane-status.ts:1344-1345). For the `sent` state, `check.text` is `"sent (to-integrator#<seq>)"` — it contains a literal space, so the printed watch-state line reads `... cut_prereview=sent (to-integrator#3)`, which is not one space-delimited token but three. This is the one field in the whole state line that violates the file's own stated invariant, and it's the one AC15 exercises for the `missing`→`sent` transition. Fix: wrap with `watchValue(...)` (yields `cut_prereview=sent_(to-integrator#3)`, consistent with every other field) or use `check.state` alone (bare `sent`) and let the one-shot listing's `prereview.line` (which already uses `.text` in `renderLaneStatus`, tools/lane-status.ts:966) be the only place the seq is shown. Either is a one-line fix; I'd lean toward `watchValue(check.text)` since it preserves the seq information the Δ line is presumably meant to surface.
- No other correctness findings. `readWatchTick`'s duplicate-basename handling (report once via `dupReported`, keep the first, never merge/overwrite) is correct and matches the degrade-honestly posture cited in the header comment. `parseWatchBaseline`/`formatWatchRearmCommand` round-trip correctly (fingerprint computed and compared consistently, `WATCH_FINGERPRINT_LENGTH`-hex validated by `FINGERPRINT_RE`).

## Quality
- No dead code or naming drift found. `checkCutPrereview`'s `notChecked(...)` helper and the `base = { specFile, mailboxFile }` spread keep the five-state branch readable.
- Judgment call flagged by the assignment — **`--mailbox-root` + `--rollup`/`--lanes`/`--all` as a usage error (tools/lane-status.ts:1220-1222)**: I read this as consistent with the spec, not in conflict with AC4 or AC15. Both ACs describe `--watch`'s own combination rules (AC4: which flags the *re-arm command* carries when given under `--watch`; AC15: `--watch --mailbox-root` specifically), and the `if (args.watch) { ... return args; }` early return means this restriction is never reached when `--watch` is set — so `--watch --lanes --mailbox-root` together (what AC4's re-arm carrying and AC15 both need) is unaffected and works. The restriction only fires for the non-watch `--rollup`/`--lanes`/`--all` ("cross"/"rollup") CLI modes, whose renderers (`rollupSameFeature`/`rollupAcrossLanes` → `renderSameFeatureRollup`/`renderCrossLaneRollup`) never read `row.cutPrereview` in the first place — so silently accepting the flag there would compute a field the CLI then drops on the floor. Rejecting it as a usage error is more honest than a silent no-op, and the CLI usage text ("`--mailbox-root <dir>` lane listing / --watch: ...") documents exactly this scope. Recommend qa-engineer confirm AC10–AC14's proof (`test/e178b-cut-prereview.test.mjs`) doesn't route through `parseLaneStatusArgs` with `--lanes`, since that combination is now a CLI usage error — the API-level `computeLaneStatus({ mailboxRoot, ... })` path (which those ACs are naturally testable against) is unaffected either way.
- **[recommended]** `readWatchTick` (tools/lane-status.ts:1494-1520) computes a `LaneWatchState` (including a `checkCutPrereview` file read, when `--mailbox-root` is set) for every lane the provider returns, even when `--lanes` restricts the watched set to a subset. Functionally correct (AC7 only constrains *which I/O primitives* run, not scope), but it's extra file I/O every tick for lanes nobody asked to watch. Low priority given typical lane counts.

## Correctness

### C1 (BLOCKING) — the E120 re-cut refusal is bypassed by an indented task row

`tools/tasks-file.ts:676` builds the void-marker scan as

```
const voidedPattern = new RegExp(`^- \\[-\\] ${escapeRegExp(taskId)}\\b`, "m");
```

The `^` anchor (with `m`) requires the marker to begin at column 0. But every
other scan in the same function normalises first — the duplicate-id re-scan at
`tools/tasks-file.ts:654` does `line.trim().match(regex)`, and `parseTasks`
itself trims at `tools/tasks-file.ts:112` — so an **indented** checkbox row is a
fully supported, parseable task throughout this file. `voidTaskInFile`'s
replacement pattern (`tools/tasks-file.ts:519`) is deliberately *un*anchored, so
voiding an indented row rewrites it in place and leaves the marker indented. The
new scan then cannot see it.

Reproduced end to end against `dist/` on this branch, with a two-space-indented
row:

```
void      -> {"success":true,"taskId":"<id>","marked":"voided", ...}
on disk   -> "  - [-] <id> indented task (voided: wrong cut)"
re-add    -> {"success":true,"taskId":"<id>","section":"Active", ...}   <-- E120 reproduces
on disk   -> the indented void marker AND a live re-cut row for the same id
```

The flat-row control in the same run is correctly refused, so the fix works only
for column-0 rows. This is the primary closure for E120 in file mode; a
whitespace prefix defeats it.

Fix: normalise before scanning — either test per-trimmed-line the way the
duplicate scan already does, or anchor as `^[ \t]*- \\[-\\] `. The identical
`^`-anchored pattern in `voidTaskInFile`'s Q1 already-voided check
(`tools/tasks-file.ts:491`) has the same hole and should be corrected in the
same edit, otherwise an indented voided row also reports "not found" on re-void.

### C2 (BLOCKING) — the E131 shape heuristic fires on voided marker rows, whose invisibility is intended

`tools/tasks-file.ts:82`:

```
const TASK_LINE_SHAPE_RE = /^- \[[ x-]\]\s+\S/;
```

The checkbox class includes `-`, so the heuristic matches the void marker row.
That row is *supposed* to be an expected strict-parse miss — the doc comment
above `voidTaskInFile` states exactly that, and the new throw's own comment says
ordinary strict-parse misses "stay silently skipped, as always". A voided row
carrying a U+2028/U+2029 in its reason text (creatable on any pre-fix build,
and creatable by hand at any time) therefore turns into a hard throw.

Reproduced: a file containing one healthy row plus one legacy voided row whose
reason carries U+2028 makes `parseTasksFromFile` throw, and with it
`completeTaskInFile` / `rollbackTaskInFile` / `voidTaskInFile` /
`getNextTaskFromFile` / `tw_detect_drift` / `tw_sync`. Only `addTaskInFile`
survives (it never calls `parseTasks`).

The thrown message is also wrong for this case: it claims the row "would
otherwise silently disappear from every reader of this file", but for a voided
row disappearing from every reader is the contract.

Fix: `/^- \[[ x]\]\s+\S/`. One character. It removes the false positive without
weakening the real E131 case at all.

## Architecture

- **Fail-loud on a corrupted row is the right call.** Judged on the merits the
  brief asked for: the throw is caught at the tool boundary (`index.ts:196`) and
  returned as an `isError` text response, not a process crash; `withFileLock`
  releases in a `finally` (`guards/file-lock.ts:101`), verified by inspection and
  by the absence of a stale `.lock` after a thrown mutator call; and critically
  the `UPDATE_STATE_GATE_PIPELINE` does **not** call `listTasks`, so
  `tw_get_state` and `tw_update_state` stay callable — the governance write path
  is not bricked and the workspace is never unrecoverable. The error names the
  file, the character class and the exact remedy. Against that, the alternative
  is the status quo the backlog row calls out as the worst property of E131: the
  erasure is invisible precisely in `tw_detect_drift`, the tool whose job is
  noticing silence. Turning that into a loud, self-describing refusal is an
  improvement, not a denial of service. This is not a finding.
- The documented residue — the shape heuristic covers the default row format
  only, so a fully custom `taskPattern` still relies on the input boundary — is
  **acceptable and should not be closed now.** Verified live: a custom-pattern
  row carrying U+2028 is still silently dropped. But the exposure is narrower
  than it reads, because such a workspace also cannot void or complete through
  the default-format mutators, and there is no general way to detect "matches an
  arbitrary caller-supplied pattern except for the terminator" without modelling
  that pattern's structure. Filed as NEW-5 rather than fixed here.
- Layering is respected: the fix sits in the task layer, the gates are untouched,
  and nothing in `gates/` was edited despite the backlog row naming
  `gates/code-review.ts` as a candidate site. Refusing at the mutator is the
  cheaper and more durable placement — it removes the state in which the bug is
  expressible instead of teaching every future evidence reader a new field.

## Correctness

### R2-C1 (BLOCKING) — C1's fix closes space and tab only; six other whitespace characters still bypass the E120 refusal

`tools/tasks-file.ts:509` and `tools/tasks-file.ts:700` both now build

```
new RegExp(`^[ \\t]*- \\[-\\] ${escapeRegExp(taskId)}(?=\\s|$)`, "m")
```

`[ \t]` is a two-character subset of what the sibling normalisation removes.
`String.prototype.trim()` strips the full ECMAScript *WhiteSpace* + *LineTerminator*
set — U+0009, U+000A, U+000B, U+000C, U+000D, U+0020, U+00A0, U+1680, U+2000–U+200A,
U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF. `parseTasks` trims
(`tools/tasks-file.ts:118`), and the duplicate-id re-scan **three lines above the new
pattern** trims per line (`tools/tasks-file.ts:671`: `line.trim().match(regex)`). So a
row indented with any of those other characters is a first-class, fully parseable live
task everywhere in this file — but is invisible to the void-marker scan, because
`voidTaskInFile`'s replacement (`oldPattern`, `tools/tasks-file.ts:539`) is
deliberately un-anchored and rewrites the row in place, preserving the indent.

Result: round 1's C1 reproduces unchanged, only with a different indent character.
Reproduced end to end against `dist/` on this branch, one temp workspace per case:

```
indent          parses as live task   void      re-void                 re-add
--------------- --------------------- --------- ----------------------- ----------------
(none)          yes                   voided    alreadyVoided           REFUSED   ok
U+0020 U+0020   yes                   voided    alreadyVoided           REFUSED   ok
U+0009 tab      yes                   voided    alreadyVoided           REFUSED   ok
U+00A0 NBSP     yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
U+000B VT       yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
U+000C FF       yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
U+2000 EN QUAD  yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
U+3000 ideogr.  yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
U+FEFF BOM      yes                   voided    "Task T-X not found."   ACCEPTED  <-- E120
```

On every ACCEPTED row the resulting `tasks.md` holds the indented void marker **and**
a live re-cut row for the same id — the exact end state E120 exists to prevent, with
`review_reports/review_<id>.md` and `qa_reports/review_<id>.md` from the voided
incarnation still satisfying both evidence gates for work nobody reviewed. The Q1
parity is lost in the same breath: re-voiding reports plain "not found" instead of
`alreadyVoided: true`.

This is not a theoretical character set. U+00A0 is what a paste out of a rendered
Markdown preview, a browser, or a rich-text editor produces; U+3000 is the ordinary
full-width space a CJK author's IME emits; U+FEFF prefixes the first line of any
UTF-8-with-BOM file. And the threat model this diff itself argues for is hand-edited
`tasks.md` — the E131 comment block at `tools/tasks-file.ts:63` names a directly
hand-edited file as "the most likely real trigger". A closure that is defeated by an
unusual whitespace character, shipped in the same cut as a hardening whose entire
premise is that an unusual Unicode character silently defeats a line-based mechanism,
is not coherent.

Cost of a complete fix is the same one line, at the same two sites. Preferred, because
it introduces no third definition of "leading whitespace" into a file that already has
one:

```ts
const voidedRe = new RegExp(`^- \\[-\\] ${escapeRegExp(taskId)}(?=\\s|$)`);
const alreadyVoided = content.split("\n").some((l) => voidedRe.test(l.trim()));
```

That is byte-identical normalisation to `parseTasks` and to the duplicate-id re-scan
directly above it, and it is what round 1 asked for ("test per-trimmed-line the way
the duplicate scan already does"); the anchor variant was the alternative offered
alongside it, and it is the one that leaks. If the regex form is preferred for any
reason, `^[^\S\r\n]*` is the minimal correct class (all whitespace except the line
breaks the `m` flag depends on) — but the per-line-trim form is the better change.

### The asymmetry, judged (item 2 of the brief) — not a defect

The concern was that `TASK_LINE_SHAPE_RE = /^- \[[ x]\]\s+\S/` is anchored at column 0
with no indentation tolerance, so an indented live row carrying U+2028 would escape the
E131 guard. It does not, because the guard does not test the raw line. At
`tools/tasks-file.ts:118` the loop computes `const trimmedLine = line.trim()` and at
`:135` tests `FORBIDDEN_TERMINATOR_RE.test(trimmedLine) && TASK_LINE_SHAPE_RE.test(trimmedLine)`.
The `^` anchor is therefore applied to an already-normalised line, and with the *full*
trim set rather than a subset.

Verified — a healthy row plus a live `[ ]` row carrying U+2028, under four indents:

```
flat     -> THREW (guard fired)
2-space  -> THREW (guard fired)
tab      -> THREW (guard fired)
U+00A0   -> THREW (guard fired)
```

So closing C1 by adding indentation tolerance at the two void-marker sites does not
re-open the silent-erasure path; the E131 guard was never indentation-sensitive.

The asymmetry the brief noticed is real, but inverted: the C2 site performs the
*correct* normalisation (`trim()`), and the C1/NEW-3 sites perform a weaker
approximation of it. Bringing the two void-marker scans onto `trim()` — the fix
R2-C1 asks for — removes the asymmetry rather than deepening it, and leaves exactly
one definition of leading whitespace in the file.

One further consequence of the trim-first ordering, noted as correct rather than as a
finding: a U+2028/U+2029 that sits purely at the start or end of a row is stripped by
`trim()` before `parseTaskLine` runs, so such a row parses normally and the guard
correctly stays silent — there is no erasure to report in that case.

### NEW-4 — fixed, verified atomic

`tools/storage-sqlite.ts:360` constructs `txVoidTask` once, over statements prepared
immediately above it (`voidTaskStmt` at `:341`, `insertVoidedTombstoneStmt` at `:350`);
both are also resolved through `this` at call time, so construction order is not
load-bearing either way. `voidTask` calls it at `:777` with four arguments matching the
four declared parameters, and `better-sqlite3` passes arguments through unchanged.

Checked against the `better-sqlite3` build vendored in this worktree, not from memory:

- the returned value is a real transaction function (`.deferred` / `.immediate` present),
  and `db.inTransaction` is `true` inside the body;
- a forced failure on the second statement rolls the first back — the deleted row was
  still present and the second table empty after the throw;

- the early `return info` on a zero-change DELETE writes no tombstone and returns

  the pre-fix behaviour, and a task that was not deleted is never tombstoned.

End-to-end SQLite behaviour is unchanged from what round 1 verified: void succeeds,
re-void reports `alreadyVoided: true`, re-add is refused with `voided: true` and the
same text as file mode, a never-existed id still reports plain not-found, the tombstone
row carries `(workspace_path, task_id, reason, voided_at)`, and the same id remains

### No false positive from `split("\n").some(...)` (item 3)

The concern was that matching per-trimmed-line is broader than the previous anchored
multiline test and might match a void marker embedded in another row's description or
note text. Verified it cannot, and that it is in fact *narrower* than round 2's form:

| case | result |
|---|---|
| `- [ ] T-A see also - [-] T-Y for context` → add `T-Y` | allowed (correct) |
| `- [ ] T-A note<U+2028>- [-] T-Y quoted marker` → add `T-Y` | allowed (correct) |
| `- [ ] T-A note<CR>- [-] T-Y quoted marker` → add `T-Y` | allowed (correct) |
| CRLF file, genuine marker on its own line | void ok / `alreadyVoided: true` / re-add refused |
| bare `- [-] T-BARE` with no description | seen, re-add refused; healthy rows still parse |
| `- [-] T-TRAIL` with trailing spaces | seen, re-add refused |
| `U+3000 U+00A0 TAB SPACE - [-] T-MIX ... U+2000` (mixed both sides) | seen, re-add refused |

The anchored `^- \[-\]` can only match at position 0 of a trimmed line, and `trim()`
removes only leading/trailing whitespace — never interior text — so a marker that appears
after any non-whitespace character on its line is structurally unmatchable. The two
U+2028/CR rows above are where round 2's `m` flag would have *false-refused* a legitimate
new id, since JavaScript's multiline `^` matches after `\r`, `\n`, U+2028 and U+2029.

control round 2 did not run: `escapeRegExp` holds for a metacharacter id — voided `T-A+B`

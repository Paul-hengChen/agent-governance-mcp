## Correctness
No required findings. Points verified adversarially:

- **Key-absent byte identity**: the `"."` path builds `primaryNm`/`laneNm` with `path.join(repoRoot, ...[], "node_modules")`, the same as base. Every templated string renders the base text when `rel = "node_modules"`, `where = "the lane"` and `pwhere = "the primary checkout"`. Confirmed by the 6-case A/B run above.
- **Symlink safety for subdir links**: segments are D2-validated (no `..`, no absolute path), so `<lane>/<loc>` stays lexically under the lane. `isRealLaneDir` refuses any symlinked segment. The existing `lstatOrNull(laneNm)` guard means a real directory, or any existing entry, is never replaced. The only primary-side call is `statSync(primaryNm)`. Adversarial probe `[".", "node_modules/pkg"]`: the root link is created first, so `node_modules/pkg` is reached *through* that link. `isRealLaneDir` rejects it (`e291.lane-dir-missing`), and the primary's `node_modules/pkg` keeps only its original `i.js`. No write goes through the link.
- **E335 temp+rename**: `materializeFindingsCopy` writes `<dst>.<pid>.<ts>.tmp` with `wx`, then `renameSync`s it over the entry. rename(2) replaces the symlink entry itself, so nothing is written through the link. On failure it removes its own temp file and leaves an existing file with the same name (`EEXIST`) alone.
- **T-E335-03 aside lifecycle**: (1) If `mkdirSync` fails before the aside rename, the guard `lstatOrNull(aside) !== null` skips the restore. Correct. (2) If `cpSync` fails part-way, the probe (chmod-000 lane file) shows the history `pending-tickets.md` restored to `OLD-HISTORY\n`, no aside left, the worktree kept, and the next run converging. (3) If the aside rename itself fails (read-only history dir), the history link is untouched, no aside exists, the error is reported and the re-run converges. (4) If `materializeFindingsCopy` fails after `cpSync`, the catch block renames the aside back over the just-copied link (an atomic replace on POSIX). (5) After success the aside is deleted, and a link is removed with `rmSync` (an unlink, never following the link). At every point the old history bytes exist either at `dst` or at `aside`, so there is no window where data can be lost.
- **Re-run idempotence**: in the refuse→refuse→ok sequence each run leaves a clean history dir, and the aside name includes pid and timestamp, so it cannot collide.
- The sr's reason for preferring rename-aside over a `cpSync` filter (with Node 22's JS copy path, a filter makes it refuse a link over an identical link) is consistent with the observed behavior: in checker case (b), `other-link.md` (identical link already in history) is re-copied without error through the unfiltered native path.

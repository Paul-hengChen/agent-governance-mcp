## Correctness

**F1 — required — `content/skill-integrator.md:164` (Stage 6 step 4, stale pull request remedy): `git merge --no-ff main` merges a stale local `main`.** Local `main` was last moved at 5b-1 (`git pull --ff-only`), before `integ/<feature>` was branched. `BEHIND` means `origin/main` moved *after* the pull request opened; nothing in Stage 6 before step 4 updates local `main` (step 4's alternative wait is `git fetch`, which updates only `origin/main`). So the literal remedy prints "Already up to date", the push is a no-op, the pull request stays `BEHIND`, and no STOP is stated for that outcome. 5b-1 of the same file already says a local `main` behind `origin/main` is "the normal state after any merged pull request", so the SOP contradicts itself here. The spec's ruling uses the same literal, so this is a spec-level gap carried into the text, but the fix stays inside AC1's wording and the grant: bring local `main` up to date first (`git switch main`, `git pull --ff-only`, `git switch integ/<feature>`, then `git merge --no-ff main`). Or merge `origin/main` after a `git fetch`. `git merge --no-ff <ref>` and `git switch <existing-branch>` are both in the integrator grant.

**F2 — required — `content/skill-integrator.md:164` vs :144 (5b-5): the remedy's push can auto-merge an unreviewed substantive resolution.** Step 3 has already armed `gh pr merge --auto --merge`, so in step 4 the push of the integration branch triggers the merge: the pull request lands as soon as the checks are green. The remedy says a conflict in the `merge --no-ff main` is handled "under 5b-4 and, when substantive, 5b-5, like any other". But 5b-5's guard, rewritten in this diff, is "never open the pull request before that verdict is APPROVED", and the pull request is already open. So nothing stops the push, and the merge it triggers, from happening before the code-reviewer verdict. Spec amendment 1 is explicit: "code-reviewer on the merge commit before the pull request may merge". As written, a merge-time resolution that no lane's PASS covers can reach `main` without review, which is the builder ≠ judge hole 5b-5 exists to close. Fix (one clause in step 4): when the resolution is substantive, push only after the 5b-5 verdict is APPROVED and its evidence file is committed, because with auto-merge armed the push is the merge trigger. CHANGES_REQUESTED → stop and report, as 5b-5 says.

**R1 — recommended — `content/skill-release-engineer.md:56` (3b) with :55 (3a recovery sentence) and :287 (new row): same-version recovery collides with 3b's STOP.** The new row and 3a route a `BEHIND` / red / `CONFLICTING` release pull request to "re-baseline at step 3a on a new branch". When `main` moved because of a non-release merge, the re-derived version is unchanged. The "new" branch name is then the same `release/vX.Y.Z`, which still exists (unmerged, its pull request open), so 3b STOPs again. The role cannot clear it: `git branch -d` refuses an unmerged branch, `-D` is forbidden, and deleting a remote branch is not on its list. The human can recover, so this is not a deadlock, but the SOP does not say who closes the stale pull request and removes the branch before re-entry. Suggest one clause on the new row or in 3b: the coordinator/human closes the stale pull request and removes `release/vX.Y.Z` before re-entry at 3a. The spec's "new branch" ruling is honored either way.
